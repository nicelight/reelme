# CanonUSB — локальная съёмка ReelMe через Canon EDSDK

Предложение для EOS 1100D на Windows 11. Решение о замене digiCamControl стоит принять после сравнения на одной камере. В реализации с digiCamControl браузер ждёт 200 мс после каждого кадра превью. Даже при мгновенном ответе это ограничивает показ пятью кадрами в секунду. Фактическую частоту самой камеры нужно измерить независимо. [Текущий клиент](../../src/client/capture/Capture.svelte)

## Идея и трудность реализации

CanonUSB должен дать посетителю плавное превью и самостоятельно возвращать изображение после потери связи. Отдельный процесс позволяет перезапустить зависшую библиотеку Canon, сохранив экран ReelMe и текущую позу. Возможность снова открыть USB-сессию после такого перезапуска зависит также от состояния камеры и драйвера Windows.

Основная трудность — цикл испытаний. По оценке команды, на тесты приходится около 80% времени разработки. На Kubuntu можно воспроизводимо проверить реакцию ReelMe на остановку потока, завершение процесса и потерю ответа после спуска. Но поведение симулятора задаём мы сами. Частоту выдачи кадров EOS 1100D, длительность паузы после снимка и способность EDSDK восстановить связь после реального сбоя USB можно установить только экспериментом с камерой. Сборка в Windows и запуск без камеры подтверждают загрузку приложения и DLL.

Для доводки нужен регулярный доступ к стенду с Windows 11 x64 и EOS 1100D. Когда воспроизводится зависание, разработчику нужно снять журнал, изменить обработку и повторить тот же сценарий на том же оборудовании. Если каждый прогон зависит от человека у удалённой фотобудки, даже небольшое изменение требует отдельного выезда или согласования. При таком режиме доступа можно подготовить прототип на Linux, но трудно оценить сроки достижения двух главных целей — плавного превью примерно при 20 кадрах/с и автоматического восстановления связи.

## Совместимость

Canon перечисляет EOS 1100D в EDSDK 13.21.10. В доступной матрице пакета **EDSDK with RAW 13.19.0** для этой модели отмечена Windows 32-bit. Для первого запуска предлагается x86-процесс на Windows 11 x64. Версию DLL и её зависимости нужно взять из официального комплекта, сверить с его таблицей моделей и зафиксировать вместе с результатом испытания. Для ReelMe достаточно передачи JPEG. [Список Canon](https://asia.canon/en/campaign/developerresources/sdk) · [Матрица разрядности Canon](https://developercommunity.usa.canon.com/resource/1744393287000/CDC_EDSDKRAW_Compat_List)

## Одна программа CanonUSB на компьютере фотобудки

Одна установка и один ярлык. Основной процесс x64 запускает дочерний x86 с соответствующей DLL Canon, следит за ним и завершает оба при выходе. В Windows 11 x64 приложения x86 исполняются через встроенную WOW64. [Совместимость Windows](https://learn.microsoft.com/windows/win32/winprog64/running-32-bit-applications)

- **Локальный сервер на TypeScript/Node.js** раздаёт существующий `reelme.html` на `localhost:5513`, принимает запросы браузера и запускает дочерний процесс. Слушает loopback. Изменяющие запросы принимает с origin установки. Браузер продолжает работать с облачным API ReelMe по ключу установки. Формат отправки серии и её завершение уже реализованы. [Облачная передача](../../src/client/capture/PhotoSession.svelte)
- **Процесс камеры на C++/Win32** загружает EDSDK и единственный открывает USB-сессию. Вызовы SDK выполняются последовательно с обработкой событий Windows и SDK по примеру из выбранного пакета Canon. У спуска и передачи оригинала приоритет перед очередным чтением видоискателя. Локальный сервер общается с процессом через каналы stdin/stdout с сообщениями известной длины. Диагностика идёт отдельно. Если вызов DLL заблокировался, сервер всё ещё отвечает браузеру и может завершить процесс.

Выбор режима — локальная настройка запуска фотобудки, применяемая между сессиями. В режиме CanonUSB собственный сервер добавляет в локальную страницу признак адаптера и версию API. В режиме digiCamControl оператор запускает digiCamControl с существующей страницей. Экран выбирает адаптер один раз при загрузке. Каждый режим использует собственные команды камеры и политику превью. Перед сменой режима нужно освободить USB и порт 5513. При занятом порте или ошибке CanonUSB экран сообщает об ошибке выбранного режима. Автоматического перехода с неопределённым результатом спуска нет.

## Live View и восстановление

Цель — около 20 свежих кадров/с в браузере, с показом в пределах 800×600 и сохранением пропорций. Бюджет составляет около 50 мс между показами. Сначала передаём JPEG видоискателя как выдала камера и масштабируем при показе. Если замеры укажут на ограничение USB, проверяем доступность меньшего режима EVF именно на 1100D. Уменьшение кадра уже на ПК не сокращает время прошедшей USB-передачи.

1. Процесс камеры читает JPEG видоискателя через `EdsDownloadEvfImage`. После успешного получения публикует номер кадра и время по монотонным часам. Сервер хранит последний кадр. Медленный клиент пропускает промежуточные кадры.
2. Браузер запрашивает `GET /camera/preview?after=<номер>&epoch=<поколение>`. Сервер сразу возвращает более свежий JPEG либо кратко ждёт его появления. После показа браузер сразу запрашивает следующий. Одновременно активен один запрос. Пустой ответ по истечении ожидания допускает повтор. Новое подключение камеры получает новое поколение, поэтому клиент сможет возобновить просмотр после сброса счётчика.
3. Сервер следит за временем последнего успешного получения кадра и за прогрессом текущей операции SDK. Во время экспозиции действует отдельный таймаут передачи фото. Кратковременная занятость вызывает повтор чтения. Устойчивая остановка превью при отвечающем SDK запускает повторное включение Live View, затем переоткрытие USB-сессии. При заблокированном вызове сервер завершает дочерний процесс, дожидается его выхода и запускает новый. При отсутствии камеры поиск продолжается с увеличиваемой ограниченной паузой.
4. Экран показывает «Восстанавливаем связь» и снимает это сообщение после первого свежего кадра. Возвращение USB возобновляет превью. Если камера требует выключения питания, после ограниченного числа попыток появляется конкретная подсказка сотруднику. Для зависания с повторной выдачей одного JPEG счётчик успешных вызовов недостаточен. На стенде перед объективом должен двигаться объект или идти секундомер. Похожесть соседних кадров неподвижной сцены сама по себе не запускает перезапуск.

## Фотография и повтор

Браузер выдаёт отдельный UUID каждому намеренному спуску, в том числе пересъёмке той же позы. Повтор HTTP-запроса сохраняет UUID. Сервер фиксирует его на диске до передачи команды процессу камеры. На один момент разрешён один незавершённый спуск. По событию передачи от Canon процесс скачивает оригинал во временный файл и атомарно публикует законченный JPEG под UUID. Браузер получает его по идентификатору, без сравнения списков файлов.

После перезапуска готовый файл можно отдать снова. Если команда могла дойти до камеры, а файл отсутствует, операция получает статус «исход неизвестен». Автоматический повтор запрашивает состояние. Новый спуск требует осознанной пересъёмки после разрешения предыдущей операции. Поздний файл с неподтверждённой принадлежностью исключается из серии.

## Разработка и испытания

| Где | Что запускаем | Что проверяем |
|---|---|---|
| Linux, ежедневно | Настоящий сервер, экран ReelMe и дочерний симулятор с тем же протоколом | Движущийся счётчик в JPEG, разрыв HTTP, остановка кадров при живом процессе, полное зависание процесса, пропажа камеры в момент спуска, повтор UUID. После восстановления вкладка продолжает работу, повторных спусков нет. |
| Windows runner для сборки, локальная VM по желанию | Сборка Win32 с официальным SDK и запуск собранного комплекта | Разрядность, загрузка DLL и зависимостей, запуск дочернего процесса, понятное состояние при отсутствии USB-камеры. На Linux-хосте с подключённой Canon можно также пробросить USB в Windows VM. |
| Windows 11 фотобудки и EOS 1100D | Сначала диагностическая утилита, затем тот же модуль вместе с ReelMe | Частота и паузы между кадрами, спуск из Live View, целый JPEG, возврат превью после спуска, извлечение и возврат USB, выключение камеры, длительная серия. |

**Первый эксперимент** — запустить небольшой x86-клиент EDSDK на установке до написания всего сервера. Сначала снять минуту движущегося секундомера в текущем ReelMe, затем минуту тем же фотоаппаратом через EDSDK. Записать частоту и 95-й процентиль интервалов, выполнить десять спусков, измерить время до первого кадра превью после каждого и время восстановления после переподключения USB. Повторить измерения в браузере после подключения нового адаптера. В журнале связать время спуска, событие SDK, завершение JPEG и восстановление превью одним UUID. Сопоставить измеренную частоту с целью 20 кадров/с и выбрать таймауты по наблюдаемым паузам.
