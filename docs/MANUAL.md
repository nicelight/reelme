# ReelMe — руководство по запуску и эксплуатации

[← На главную](../README.md) · Команды выполняются из корня репозитория.

Редактор сюжетов на Svelte 5 / Vite и сервер TypeScript / Fastify с SQLite.
Администратор загружает материалы и сохраняет V2V/P2V-сюжеты для 11 согласованных
моделей. Вход оператора сохраняется до выхода, администратора — 30 дней.
Локальный каталог показывает видимые сюжеты и создаёт сессию со снимком настроек.
Локальная съёмка проверена по HTTP-контракту digiCamControl. JPEG сохраняются
на сервере; после подтверждения приёма посетитель получает номер, а установка
освобождается. Сервер обрабатывает все 11 согласованных моделей через fal, сохраняет и проверяет видео.
Готовый результат получает собственную ссылку скачивания и форму email.
Почтовый обработчик отправляет результат, общий экран показывает прогресс и QR,
а архив сохраняет доступ к прошедшим мероприятиям для обоих аккаунтов.

## Запуск с чистого checkout

Нужны Node.js **22.13+** (проверено на 22.22.1), npm и FFmpeg/ffprobe в `PATH`.
На Debian/Ubuntu: `sudo apt-get install ffmpeg`. Если для вашей платформы нет готового
бинарного `better-sqlite3`, установите Python 3, make и C++ compiler для node-gyp.

```bash
npm ci
cp .env.example .env
chmod 600 .env
```

В `.env` задайте `ADMIN_PASSWORD` и `OPERATOR_PASSWORD` (12–256 символов).
Не используйте реальные пароли в командной строке или Git. Затем:

```bash
npm run setup
npm run check
npm run build
npm start
```

Откройте нужную страницу (локально замените домен на `http://localhost:3000`):

- [Главная](https://reelme.natureonzoom.win/) — публичные сюжеты и превью; выбор и съёмка отключены.
- [Админка](https://reelme.natureonzoom.win/admin) — редактор и настройки, только `admin`.
- [Сегодня / Архив](https://reelme.natureonzoom.win/operator) — рабочая страница `admin` и `operator`.
- [Экран результатов](https://reelme.natureonzoom.win/results) — полноэкранный показ для обоих аккаунтов.

Логины: `admin` и `operator`. «Открыть экран» открывает `/results` в новой вкладке
того же профиля. Старый `/?screen=results` перенаправляет туда же. Раздел «Экран
результатов» в админке настраивает показ. Главная остаётся промогалереей после входа.

`setup` создаёт SQLite, два аккаунта и случайный ключ установки в
`DATA_DIR/installation-key.txt` с правами `0600`; сам ключ не выводится в лог.
После успешного `setup` удалите пароли из `.env`: сервер использует сохранённые
scrypt-хеши, а не эти переменные. Повторный `npm run setup` не меняет пароли, ключ,
сюжеты или материалы и не требует паролей для уже созданных аккаунтов.

`APP_ORIGIN` должен точно совпадать с адресом браузера, без завершающего `/`.
Для другого порта измените и `PORT`, и `APP_ORIGIN`. HTTP разрешён только для
loopback-разработки; внешний origin требует HTTPS. На VPS TLS завершает Caddy,
backend по умолчанию слушает `127.0.0.1`. Приложение работает на `nskserver`
за CGNAT через SSH-туннель к VPS `nskigorprod`.
[Ранбук сборки и развёртывания](../deploy_to_nskserver.md) разрешает сборку
на nskserver (32 GB RAM) или рабочем компьютере:
в контейнере backend слушает `0.0.0.0`, на хосте порт опубликован только на loopback.
Не открывайте каталог данных через Caddy.

## Постоянные данные

По умолчанию `DATA_DIR=./var`, относительно рабочего каталога сервера:

- `reelme.sqlite`, `reelme.sqlite-wal`, `reelme.sqlite-shm` — SQLite и служебные файлы;
- `media/` — оригиналы материалов с уникальными идентификаторами;
- `media/sessions/<sessionId>/<uuid>.jpg` — оригинальные фотографии по сессиям;
  позиции поз и метаданные записаны в SQLite (`capture_photos`);
- `installation-key.txt` — секрет установки, не клиентский asset.

Для сервера рекомендуется абсолютный `DATA_DIR`, например `/srv/reelme-data`.
Каталог создаётся при первом запуске и должен находиться отдельно от `dist/`.
Сборка заменяет клиентские assets, но не данные. После остановки и повторного
`npm run setup && npm start` сохранённые слоты и файлы остаются доступными.
Заменённые материалы остаются доступны сессиям, которые уже ссылаются на них.
При очистке мероприятий материал удаляется только тогда, когда на него больше
не ссылаются текущие слоты и снимки других сессий.

## Работа с редактором

Войдите как `admin`, создайте сюжет, добавьте изображение и описание, выберите
режим и модель. В списке — миниатюра, первые три слова описания и видимость.

Порядок настройки: модель → 1/2 человека или группа 3+ → число кадров → параметры
видео → «Зафиксировать параметры генерации». После фиксации доступны материалы, промпт и тесты.
«Изменить параметры генерации» очищает нижние настройки и ручной промпт, сохраняя карточку слота,
привязанный V2V-ролик и кеш тестовых фото. Совместимые верхние значения сохраняются.

- **V2V:** исходное видео необходимо для запуска; без него сохраняется черновик,
  недоступный в каталоге посетителя. Recast снимает один кадр каждого из 1/2 людей;
  его промпт редактируемый, но рекомендуется оставить пустым. Администратор
  подтверждает непрерывные кадры не длиннее 15 секунд. Дополнительные references
  доступны только в моделях, которые их поддерживают.
- **P2V:** 1–4 кадра на человека или группу; у индивидуальных Kling — 2–4 разных
  ракурса на Element. Количество дополнительных фото зависит от модели и набора.
  Демовидео необязательно и не входит в генерацию.
- Разрешение, ориентация, ratio и длительность ограничены возможностями endpoint.
  Без `aspect_ratio` ориентация определяется исходным видео. Crop/upscale не выполняются.
  Для H3 Reference сохраняется `promptExpansionMode: disabled`.
- Готовый текст загружается целиком из `.md` по [матрице](../docs/slot-setup/matrix.md).
  Изменение references сохраняет ручную правку с напоминанием проверить ссылки;
  смена верхнего setup сбрасывает её. Описание слота в промпт не подставляется.

Для V2V редактор показывает ID слота и ожидаемое имя
`<slot-id>__landscape.mp4` / `<slot-id>__portrait.mp4`. Подготовьте файл в
`media/template-videos` (либо `TEMPLATE_VIDEOS_DIR`), нажмите «Подключить исходник из
файла» и сохраните слот. Плеер показывает тот же исходник, который получает модель.
После замены файла нажмите «Обновить исходник из файла» и сохраните: старые сессии
останутся на прежней копии. Подробнее — [подготовка роликов](../media/template-videos/readme_media.md).

Раздел администратора «Образцы ракурсов» управляет пятью изображениями подсказок.
Замены применяются к новым сессиям; образцы не входят в генерацию. Без загруженного
изображения сохраняется текстовая инструкция. Камера показывает закреплённый образец во время отсчёта.

Загрузки: JPEG, PNG, WebP (однокадровые изображения до 40 мегапикселей), MP4/MOV.
Общий технический предел загрузки — 300 MB; меньший лимит видео конкретной модели
проверяется при сохранении. Изображения декодируются, видео проверяются через ffprobe.
При ошибке файл не становится материалом слота. Клиентская проверка не заменяет серверную.

У каждого поля статичного изображения показаны компактные рекомендуемые размеры:
обложка — 2:3, 600 × 900 px, с главным объектом в центре для обрезки в карточках;
образец ракурса — 3:5, 300 × 500 px, показывается целиком. Размеры рассчитаны для
экрана Full HD (1920 × 1080), без запаса для повышенной плотности пикселей; в широком
превью без демовидео обложка немного увеличивается. Дополнительные референсы идут
в модель: сохраняйте исходные пропорции, ориентир — 1024 px по длинной стороне.
Маленькие исходники увеличивать не нужно. Это рекомендации, технические ограничения
загрузки не меняются. У тестовых JPEG остаются отдельные ограничения ниже.

В панели «Тесты» выберите **Режим генерации** и сохраните слот:

- **fal.ai — реальная генерация** — обычный платный запрос; по умолчанию.
- **Только проверка входных данных** — JPEG, материалы и запрос модели проверяются,
  но видео/QR/email не создаются. Это прежнее поведение флага фейковой генерации.
- **Тестовое видео — полный проход без fal** — после проверки входов и короткого
  ожидания возвращается один из двух встроенных роликов с надписью «ТЕСТОВОЕ ВИДЕО».
  Далее работают настоящий FFmpeg, экран результатов, QR, скачивание и email.
  Письмо отправляется через настроенный SMTP; без него останется pending.

Для полного ручного прохода выберите третий режим у видимого слота, сохраните и
пройдите обычную съёмку. Откройте экран результатов как operator или admin, отсканируйте QR,
скачайте видео или подтвердите свой email. Для проверки без камеры загрузите
полный набор тестовых JPEG и используйте кнопку запуска в админке.

Оба тестовых режима работают без FAL_KEY, но не проверяют fal и внешнюю доступность
входных URL. Режим закрепляется при старте: последующая правка слота и рестарт
его не меняют. Старые включённые эмуляции остаются проверкой входов. Тестовое видео
помечено в операторском интерфейсе и архиве и не заменяет последний реальный ролик.
Обычные правила хранения и очистки действуют; тестовые результаты не удаляются через fal.

Для каждой тестовой позиции нужен свой JPEG до 20 MiB и 40 мегапикселей.
Сохраните полный набор и слот, затем нажмите «Отправить тестовую генерацию».
Неполный набор можно продолжить собирать в редакторе, но тест не запустится.
Кеш назначений переживает смену setup; группа и индивидуальные кадры не смешиваются,
лишние фото не отправляются. Байты JPEG не сохраняются в localStorage.
Скрытые сюжеты доступны для теста администратора. Только уже существующие legacy-тесты
с одиночным источником продолжают прежний путь; новые наборы не размножают один JPEG.

Статус теста и безопасная ошибка видны под кнопкой. При потерянном ответе повторите
запрос: браузер сохраняет его ID, в том числе после перезагрузки, чтобы не создать
вторую генерацию. После подтверждённого ответа новый запуск создаёт новую сессию.
Настройки и JPEG уже принятого теста не меняются при последующей правке слота.

Ниже находится последний ещё хранимый **реальный** готовый ролик этого слота.
Эмуляция, ошибка и незавершённая генерация его не заменяют. Плеер доступен только
администратору и читает собственный MP4 сессии по стабильному URL с Range, не открывая
форму посетителя. «Отправлено в fal» показывает время Новосибирска; «До готового видео»
включает очередь fal, скачивание и проверку локального результата. Это не чистое
время вычисления модели. Для старых строк с неизвестными временами — «Нет данных».
Удаление мероприятия убирает его ролик; отдельная копия «последнего видео» не хранится.

## Локальная страница съёмки

При выборе первого сюжета дня откроется «Новое мероприятие»: введите название,
выберите количество участников (0–50, 50–100, 100–300 или 300–1000) и локацию
(по умолчанию Новосибирск). «Сохранить» запишет данные и продолжит съёмку;
«Пропустить» создаст мероприятие с именем `Session_N`. Для следующих посетителей
этого дня форма не повторяется, в том числе после перезапуска. Днём мероприятия
по-прежнему считается календарный день Новосибирска. Название и локация видны
в архиве прошедших дней; тестовые генерации из админки не заменяют этот шаг для
первого посетителя.

В админке вкладка **«Фотобудка»** содержит сжатый план для Windows с раскрывающимися
подробностями: digiCamControl, камера, веб-сервер, размещение HTML, ключ установки,
тестовый и реальный запуск, ежедневная памятка и помощь при сбоях. Кнопка
«Скачать страницу ReelMe» выдаёт `reelme.html` из канонического шаблона с адресом
того сервера, на котором открыта админка; ключи в файл не включаются.

Страница съёмки — **http://localhost:5513/reelme.html на компьютере с камерой**.
Она работает с сервером через `https://reelme.natureonzoom.win/capture-loader.js`.
Для работы с production оставьте этот адрес в `WebServer/reelme.html` без изменений.

На Windows скопируйте файл в папку `WebServer` digiCamControl. Подключите камеру
по USB, включите WebServer и `AllowWebserverActions`, настройте JPEG и уникальные
имена файлов. Закройте другие программы, захватывающие камеру.

На Linux подготовьте страницу и запустите bridge:

```bash
mkdir -p /tmp/reelme-capture
cp WebServer/reelme.html /tmp/reelme-capture/reelme.html
python3 linux_digiCamControl/linux_digicamcontrol.py list --json
python3 linux_digiCamControl/linux_digicamcontrol.py serve --camera /dev/video0 --web-root /tmp/reelme-capture
```

Укажите устройство из списка (`/dev/video0` для V4L2 или ID gphoto2 для камеры).
ReelMe обращается к API камеры на том же origin. Подробности и зависимости —
[Linux bridge](../linux_digiCamControl/README.md). Порт 5513 должен быть свободен.

Только для разработки с локальным сервером замените origin загрузчика в копии:

```bash
sed 's|https://reelme.natureonzoom.win|http://localhost:3000|g' WebServer/reelme.html > /tmp/reelme-capture/reelme.html
```

Без камеры можно проверить загрузку страницы статическим сервером вместо bridge:
`python3 -m http.server 5513 --bind 127.0.0.1 --directory /tmp/reelme-capture`.
Это не проверяет съёмку.

Откройте **http://localhost:5513/reelme.html**. Загрузчик читает manifest текущей
сборки, подключает облачные JS/CSS и монтирует Svelte в локальном origin.
Он не перезагружает уже открытую страницу. Сервер разрешает CORS для
`http://localhost:5513`; секрет установки не входит в HTML, URL или общую сборку.
Настройщик один раз открывает **http://localhost:5513/reelme.html#setup** и вводит
ключ из `DATA_DIR/installation-key.txt` (production: `/srv/reelme-data/installation-key.txt`
на nskserver). Он сохраняется только в этом браузерном
профиле после проверки сервером; облачные cookies не нужны. Вернитесь на
`http://localhost:5513/reelme.html` для работы посетителя. Не передавайте ключ
в URL и не включайте его в HTML. После очистки localStorage настройку нужно повторить.

Каталог объединяет все доступные включённые сюжеты в одну карусель без страниц;
одновременно видны до пяти карточек. Выбранная карточка раскрывает описание и
исходное V2V-видео либо необязательное P2V-демо; без видео остаётся референсный кадр.
«Выбрать этот сюжет» создаёт сессию с сохранённым планом кадров участников или группы.
Экран показывает образец и «Начать съёмку». Далее идут отсчёт 3–2–1, звук и
подтверждение кадра; перед вторым человеком требуется готовность. Зеркалится только
Live View, оригинальный JPEG не меняется. «Продолжить без превью» сохраняет съёмку
и подсказки; при ошибке превью этот режим включается автоматически.

Пауза останавливает отсчёт, продолжение начинает полные 3–2–1. «Restart фотосессия»
очищает локальную серию и ждёт запуска с первого кадра. «Перефоткать последнее»
возвращает последнюю завершённую позицию, сохраняя остальные. Пока камера получает
JPEG, повторный затвор и пересъёмки недоступны, включая ошибку с ещё ожидаемым файлом.

После последнего снимка можно проверить серию и переснять последний кадр.
Только «Завершить фотосессию» начинает передачу JPEG. После этого доступны передача
и её повтор без нового затвора; уже принятые позиции пропускаются. Только после
подтверждения сервера появляется номер и «Следующий посетитель». Номер дополняется
нулями до трёх цифр (001, 002, …); следующий посетитель не ждёт генерации предыдущего.

Запрос старта, receipt и небольшой маркер передачи живут в sessionStorage;
ключ установки — в localStorage. JPEG Blobs хранятся только в памяти вкладки.
После reload серверные позиции сохраняются. Если передача началась, но оставшиеся
Blobs потеряны, интерфейс явно останавливает продолжение сессии и позволяет начать
новую; принятые старые кадры не стираются и не подменяются. Полный принятый набор
можно дозавершить, финализированная сессия показывает номер. IndexedDB не используется.

В digiCamControl включите WebServer, AllowWebserverActions, сохранение JPEG
и неповторяющиеся имена файлов. Перед работой остановите DSLR Remote Pro;
удалять или перенастраивать его не нужно. Единственным владельцем камеры
во время съёмки должен быть digiCamControl.

Адаптер читает `/filelist.json` перед командой затвора и ждёт новый JPEG,
затем скачивает его `Original`. Ожидание — до 30 секунд за попытку, опрос —
каждые 500 мс. «Повторить» сохраняет предыдущие Blob. Если команда затвора уже
отправлена, повтор продолжает ожидать/скачивать текущий кадр без нового затвора:
потерянный HTTP-ответ не доказывает, что камера не сняла. Если файл так и не появился,
нужна помощь сотрудника; нельзя переходить к следующей позе или посетителю.
При сбое чтения списка до затвора повтор заново запускает текущий шаг.

Live View открывается через `/liveview.html?CMD=LiveViewWnd_Show`; превью читается
из `/liveview.jpg` без кэша примерно раз в 200 мс после предыдущего ответа.
Когда Live View запущен, используется `LiveView_Capture`, иначе — `Capture`.
Отключение отображения превью не закрывает окно Live View на камере.

Эти операции проверены на управляемых HTTP-ответах. Реальная совместимость
Windows 11 Pro / Canon EOS 1100D / digiCamControl, звук на установке и переключение
с DSLR Remote Pro принимаются в TASK-005; стенд не является аппаратным испытанием.

## Разработка и проверки

```bash
npm run dev       # сборка клиента + сервер в watch; после правок UI повторить build:client
npm run check     # Svelte и TypeScript
npm test          # API/SQLite, JPEG/finalize/access/restart и HTTP-контракт камеры
npm run build     # production assets + сервер
npx playwright install chromium
npm run test:ui   # браузерные сценарии на временных данных; нужные тестам порты должны быть свободны
```

Сервер отдаёт `/`, `/admin`, `/operator` и `/results`, assets — `/assets/`; Vite dev server для авторизации
не используется. Изменяющие аккаунтные запросы требуют `Origin: APP_ORIGIN`.
Сессия — HttpOnly/SameSite=Strict cookie, с Secure при HTTPS. Для оператора cookie
обновляется при использовании, серверного срока истечения нет; ограничения браузера
на хранение cookie остаются. Выход отзывает текущую сессию в SQLite.

API редактора: `GET /api/admin/slots`, `GET /api/admin/slots/:id`,
`POST /api/admin/slots`, `PUT /api/admin/slots/:id`,
`POST /api/admin/slot-media` (multipart, поле `file`),
`GET /api/admin/slot-media/:id` (защищённые байты, поддержка Range),
`GET /api/admin/slot-media/:id/info` (метаданные).
JSON слота — `SlotInput` из `src/shared/scenarios.ts`; `id` возвращает сервер.
Оператор и валидный installation bearer получают `403`, отсутствие/неверные
credentials — `401`. Роль из тела запроса не используется.


API установки: `GET /api/catalog?page=1`, `GET /api/catalog/:id`,
`GET /api/catalog/:id/media/:mediaId`, `POST /api/capture/sessions`,
`GET /api/capture/sessions/:id`, `PUT /api/capture/sessions/:id/photos/:poseIndex`,
`POST /api/capture/sessions/:id/finalize`.
Каждый запрос требует `Authorization: Bearer <ключ>`; аккаунтная cookie ключ не заменяет.
Старт принимает `{startRequestId, slotId}` (UUID) и возвращает `StartReceipt`
из `src/shared/capture.ts`: ID сессии, дату, номер и план поз. Первый ответ — 201,
повтор — 200. Повторный ключ с другим слотом — 409. Дата фиксируется по
`Asia/Novosibirsk`, номера уникальны внутри даты, новый день начинает нумерацию с 1.

Снимок в `capture_sessions.snapshot` содержит конкретные старые media IDs и
отдельные параметры генерации; правка слота его не меняет. Демовидео находится
вне `generation`. Сессия принимает фото в состоянии `capturing`.
PUT принимает один multipart `file` с MIME `image/jpeg` (20 MiB, 40 MP), проверяет
декодирование и сохраняет исходные байты. Допустимы только позиции сохранённого
плана, до индекса 7; повтор заменяет указанную позицию. Legacy-сессии без нового
плана сохраняют прежние 1/4 фото и старые позы.
GET/PUT/finalize возвращают `CaptureStatus`: принятые индексы, `complete` и `finalized`
вместе с серверными датой, номером и планом. После finalize фото неизменяемы.
Неполный набор или попытка записи после finalize дают 409; неверный JPEG/индекс —
400, превышение размера — 413. Без ключа/с неверным ключом — 401, с одной лишь
аккаунтной cookie — 403. Файлы не доступны через публичный каталог assets.

Finalize атомарно переводит полный набор в `submit_pending` один раз. Это
сохранённая граница передачи обработчику генерации. Повтор finalize возвращает
текущее состояние; рестарт сохраняет записи и JPEG. Обработчик работает и без
`FAL_KEY`: эмуляция завершается обычным образом, реальный запрос получает
`failed / FAL_NOT_CONFIGURED`. Изолированные тесты съёмки явно отключают worker.

## Генерация видео

Для включения задайте `FAL_KEY` в серверном `.env` и доступный fal HTTPS
`APP_ORIGIN`. Ключ не передаётся браузеру. На localhost без публичного HTTPS
генерация с ключом не запускается. Входные фото и видео остаются на сервере:
`/provider-media/:token` открывает один файл без аккаунта, поддерживает Range;
неизменный материал получает один и тот же URL. Токены не разрешают просмотр
каталога/админки; защищённые маршруты материалов сохраняют свои права.

Обработчик в том же Fastify-процессе каждые 3 секунды продвигает сессии по состояниям
`submit_pending → observing → preparing → ready`, не удерживая HTTP съёмки. В запрос Recast
попадают 1/2 фото, видео, разрешение и необязательный непустой prompt сохранённого снимка. fal SDK
оставляет retries включёнными, отключает fallback, задаёт `Store-IO:0` и срок
CDN-файла 86400 секунд. После подтверждённого `request_id` новый submit запрещён;
рестарт продолжает polling/result. Явный отказ submit завершает сессию ошибкой,
отсутствие подтверждения допускает повтор и возможный дубль.

Остальные десять моделей используют тот же обработчик. У Kling индивидуальные
наборы по 2–4 фото образуют отдельный Element на человека; группа передаётся
обычными изображениями перед дополнительными references. H3 Reference, Vidu и
Gemini получают сначала упорядоченные кадры участников, затем фото сюжета. Промпт сохраняется без переписывания; подсказки
синтаксиса ссылок доступны в редакторе. O1/O3 допускают до 2500 символов, Vidu —
до 5000. O1/O3 не получают фиктивное разрешение, O3 Reference получает строковую
длительность, H3 Reference — `prompt_expansion_mode: disabled`. Демовидео P2V
не включается в запрос. Модель, параметры и материалы берутся из снимка сессии.

Состояние fal и метаданные результата хранятся в `generation_jobs`. Результат
скачивается потоком в `DATA_DIR/media/sessions/<sessionId>/result.mp4`, полностью
декодируется FFmpeg; `result.jpg` — извлечённый кадр. Непустые проверенные файлы
фиксируются в БД после записи. Сбой скачивания повторяет получение сохранённого
URL; рестарт после успешной проверки не скачивает файл повторно. Пустой/повреждённый
результат и терминальная ошибка fal дают `failed`, сохраняя сессию и фотографии.
GET capture-state возвращает безопасный `error: {code, message}`; подробности
пишутся только в серверный лог с удалением ключей, токенов и URL.

Публикация `ready` проверяет сохранённые видео, кадр и основное фото, затем атомарно
сохраняет две разные случайные ссылки в `session_delivery`. При старте сервера
подготовленные файлы также проходят эту границу, даже без `FAL_KEY`; повторного
скачивания не требуется. Готовность не зависит от состояния письма.

`npx tsx --test tests/generation.test.ts tests/model-generation.test.ts` проверяет обработку на управляемом fal
транспорте и синтетических медиа с настоящими SQLite/FFmpeg. Реальный fal API
по решению оператора не входит в обязательную приёмку разработки; его доступность,
баланс и результат реальной генерации этими тестами не подтверждаются.
Сверка десяти новых payload с официальными схемами и результаты локальных проходов —
[TASK-007 evidence](../.tasks/TASK-007-T2-FT-003-W5/evidence.md).

## Форма получения и скачивание

`/receive/:token` — анонимная форма с исходным основным фото и номером своей сессии.
Она принимает email, показывает ожидание, отправку, подтверждённый успех или ошибку
и опрашивает состояние каждые 3 секунды во время ожидания. Введённый адрес после
приёма очищается и не возвращается публичным API. QR общего экрана ведёт на эту форму.

- `GET /api/receive/:token` возвращает `ReceiveStatus` из `src/shared/receive.ts`.
- `POST /api/receive/:token/opened` сохраняет первое открытие без запуска срока скрытия.
- `POST /api/receive/:token/email` принимает `{ "email": "visitor@example.test" }`:
  атомарно сохраняет адрес, первое подтверждение и `pending`; при необходимости
  также фиксирует открытие. Неверный адрес — 400, повтор при pending/sending/sent — 409.
  После failed можно исправить адрес и повторить; первое подтверждение не меняется.
- `/api/receive/:token/photo` и `/frame` открывают только материалы этой сессии.
- `/download/:token` — отдельная ссылка на MP4 с именем `reelme-<номер>.mp4`.
  Она не ведёт в форму. Receive-токен не подходит для скачивания, download-токен — для формы.

`session_delivery` сохраняет токены, opened_at, email_confirmed_at и независимый
email_state (`not_requested/pending/sending/sent/failed`). Почтовый обработчик
включается серверными SMTP-настройками; без них принятый адрес остаётся pending.
`readyCard(db, origin, sessionId)` в Sessions подготавливает фото, кадр, номер и URL
формы для будущих защищённых экранов; функция не публикует список посетителей.
Ссылки сохраняются после рестарта и перестают работать после удаления записи сессии.
Номер не является секретом; capability-токены не дают прав аккаунта/установки.

`npx tsx --test tests/receive.test.ts` проверяет выдачу, границу ready, рестарт и
правила email на настоящих SQLite/FFmpeg. После `npm run build` браузерный проход:
`npm run test:ui -- tests/receive.spec.ts` (свободный порт 3198). Состояния отправки
в тесте задаются локально; fal и SMTP не вызываются. Доказательства —
[TASK-008 evidence](../.tasks/TASK-008-T3-FT-003-W5/evidence.md).


## Отправка писем

Укажите серверные `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`
из кабинета SMTP.BZ; адрес отправителя должен быть верифицирован. Порт по умолчанию
465 использует TLS сразу, остальные порты (обычно 587) требуют STARTTLS. Проверка
сертификата включена, минимальная версия TLS — 1.2. Частично заполненная конфигурация
не допускает старт сервера. Все пять пустых настроек отключают отправку для разработки.
Credentials не попадают в клиентскую сборку; SMTP debug и вывод писем отключены.

В единственном серверном процессе отдельный обработчик раз в секунду забирает
`pending` и фиксирует `sending` до сетевого вызова. Форма и генерация не ждут SMTP.
Видео читается с диска потоком как MP4-вложение `reelme-<номер>.mp4`.
После положительного ответа SMTP фиксируются `sent` и время отправки. Это принятие
почтовым сервисом, а не подтверждение получения или прочтения посетителем.

При ошибке чтения вложения либо явном отказе SMTP по размеру/типу отправляется одно
резервное письмо с собственной `/download/:token` ссылкой на тот же результат.
Обычный отказ адресата/политики, авторизации, соединения или потеря ответа не запускают
резервное письмо. Ни одна ошибка не повторяется автоматически: форма предлагает
ручной повтор с исправлением адреса и предупреждает, что письмо могло уже уйти.
Рестарт продолжает сохранённые `pending`, а незавершённые `sending` переводит в `failed`
с неопределённым исходом. После `sent` новый запрос запрещён; первое подтверждение
формы, состояние генерации `ready`, фото и видео не меняются. SIGTERM ожидает текущую попытку;
SMTP имеет таймаут подключения/приветствия 15 с и сетевой таймаут бездействия 60 с.
Запускать только один процесс приложения для одной БД.

`npx tsx --test tests/email.test.ts` проверяет настоящий Nodemailer через SMTP-сервер
на loopback: MIME/MP4, резервную ссылку, отказы, потерю ответа, рестарт и ручной повтор.
`npm run test:ui -- tests/email.spec.ts` после `npm run build` проверяет существующую
форму с тем же настоящим обработчиком и локальным SMTP (свободный порт 3197).
Никакие внешние письма и live fal в этих проверках не отправляются.
Реальная доставка SMTP.BZ, лимиты вложений и подпись тарифа не проверены: оператор
отменил обязательную реальную отправку на этапе разработки.
Результаты — [TASK-009 evidence](../.tasks/TASK-009-T3-FT-004-W6/evidence.md).

## Общий экран посетителей

Оператор после входа видит сегодняшние истории по дате `Asia/Novosibirsk`.
Карточка содержит только кадр готового ролика, номер и QR формы получения.
Прогресс подготовки вынесен в восемь неподвижных слотов шапки (две колонки по четыре);
нажатие строки скрывает блок, `StatusShow` возвращает его. Полный email публично не показывается.

Общий экран открывается оператором через «Открыть экран» (`/results`).
Готовые истории показываются в сетке 3×3: новые появляются через центр,
затем участвуют в круговой очереди. При перезагрузке уже готовые результаты
показываются без повторной анимации появления. Администратор в разделе
«Экран результатов» выбирает интервал страницы: 10/20/30/40/50/60 секунд;
изменение действует со следующей страницы. Прогресс подготовки находится
в шапке, ошибки и эмуляции — в операторском интерфейсе управления.
Подробные правила — [очереди и страницы](../.memory-bank/states/results-display.md).

`GET /api/display/today` и `/api/display/:id/{photo,frame,qr}` доступны
оператору и администратору. Ключ установки и receive/download-токен эти
права не дают. Фото и QR загружаются без фиксации открытия формы. Только переход
по QR и открытие формы переводят историю в этап 5; успешный почтовый обработчик —
в этап 6. QR ведёт на существующую `/receive/:token`, а не на скачивание.

Первое подтверждение email задаёт сохранённый срок скрытия — ровно 180 секунд.
История исключается из будущих очередей и страниц, но уже показанная карточка
остаётся до смены текущей страницы, чтобы не оставлять пробел. Рестарт, reload,
ошибка или повтор письма срок не продлевают. Это не удаление: записи, фотографии,
видео, форма и download остаются до удаления мероприятия. После смены дня
общий экран показывает новый день; прежние истории доступны в архиве.

Проверки: `npx tsx --test tests/display.test.ts`; после `npm run build` —
`npm run test:ui -- tests/display.spec.ts tests/results-screen.spec.ts`.
Фактические результаты и ограничения — в [TASK-020](../.memory-bank/tasks/TASK-020-T2-FT-004-W17.task.json).
Браузерные проверки используют локальный backend и тестовые данные, без внешних fal/SMTP-вызовов.


## Архив мероприятий

После входа на `/operator` оператор и администратор открывают раздел «Архив». Сервер включает
только прошедшие календарные дни `Asia/Novosibirsk`, от новых к старым; сегодняшний
день недоступен и через прямой запрос. Карточка показывает точные размеры в байтах:
«Фотографии» — оригиналы посетителей и кадры результатов, «Видео» — сохранённые
собственные результаты. Каждый файл учитывается один раз по метаданным; общие
миниатюры, референсы, исходные и демонстрационные видео слотов в объём не входят.
Прерванная съёмка учитывает только уже принятые файлы.

Нажатие на дату открывает номера и миниатюры из сохранённых снимков сюжетов.
Нажатие на миниатюру готовой истории открывает её собственное видео. Истории без
готового результата остаются в галерее с подписью и без кнопки воспроизведения.
Правка текущего сюжета не меняет историческую миниатюру. Просмотр архива и видео
не открывает форму посетителя и не меняет времена или состояния выдачи.

`GET /api/events` возвращает `{date, photoBytes, videoBytes}[]`;
`GET /api/events/:date` — `{date, sessions}` с номером, описанием, `thumbnailUrl`
и `videoUrl` (null до готовности). Медиа `/api/events/:date/:id/thumbnail` и
`/video` требуют аккаунт оператора или администратора и проверяют принадлежность
сессии дню; видео поддерживает Range. Ключ установки и receive/download-токены
не дают доступа к архиву. Скрытие общего экрана через три минуты не удаляет
архивные записи и файлы.

Проверки: `npx tsx --test tests/archive.test.ts`; после `npm run build` —

## Удаление и срок хранения

Администратор удаляет прошедший день кнопкой «Удалить мероприятие»: подтверждение
перечисляет удаляемые данные, «Отмена» ничего не меняет. Оператору кнопка недоступна.
`DELETE /api/events/:date` требует admin и правильный Origin; сегодняшний и будущие
дни отклоняются. Успех — 204. Сначала сохраняется признак удаления: день скрывается,
capture/receive/download, архивные медиа и provider-ссылки его фото закрываются.

При запуске сервера и затем каждый час тот же обработчик удаляет дни старше
14 календарных дней `Asia/Novosibirsk` и продолжает незавершённую очистку. Ровно
14 дней ещё хранятся. Удаляются собственные каталоги сессий, фото, видео, кадры,
записи и ссылки. Материалы сюжетов удаляются только когда ни текущие слоты, ни
снимки других сессий на них не ссылаются. Поздние результаты генерации не
публикуются; новые письма и резервная отправка после удаления не запускаются.
Уже принятое почтовым сервером письмо не отзывается, его download-ссылка закрыта.

Для сохранённых выходных URL вызывается
[fal delete API](https://fal.ai/docs/documentation/model-apis/fal-cdn#deleting-files)
с серверным `FAL_KEY` (нужно право `assets:write`). Ошибка или отсутствие ключа
логируется как `FAL_DELETE_FAILED` и не блокирует локальную очистку. Это не
подтверждает удаление внешней копии или внутренних данных модели; для новых
результатов по-прежнему задан срок CDN 86400 секунд. Ошибка локальной очистки
сохраняет маркер для следующей проверки/рестарта (`EVENT_CLEANUP_FAILED`).

Проверки: `npx tsx --test tests/cleanup.test.ts`; после `npm run build` —
`REELME_BROWSER_ARTIFACTS=.tasks/TASK-012-T3-FT-005-W9 npm run test:ui -- tests/cleanup.spec.ts`
(свободный порт 3195). Все удаления ограничены временными SQLite/медиа, fal delete
подменяется локальным transport. Реальные внешние удаления не выполняются.
