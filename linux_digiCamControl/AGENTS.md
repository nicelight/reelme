# AGENTS — linux_digiCamControl

## Назначение и границы

Проект служит локальным заменителем **части HTTP API digiCamControl** для разработки
ReelMe на Linux. Он не запускает Windows-программу, не использует Canon EDSDK и не
доказывает совместимость Canon 1100D с Windows 11. Последняя проверяется отдельно
на установке заказчика. Гарантии 0,5 с от команды до получения JPEG нет.

Контекст ReelMe: пользователь выбирает видеослот, видит позы и обратный отсчёт,
получает несколько кадров для дальнейшей обработки. Этот сервер знает только о
фотографировании и файлах, не о слотах, моделях AI и облачной бизнес-логике.
Существующая Windows-установка Breeze/DSLR Remote Pro не затрагивается.

## Быстрая проверка

Из корня проекта:

```bash
python3 linux_digicamcontrol.py list --json
python3 linux_digicamcontrol.py serve --camera mock
# Во втором терминале:
curl -s http://localhost:5513/health
curl -s 'http://localhost:5513/?CMD=Capture'
curl -s http://localhost:5513/status.json
curl -s http://localhost:5513/filelist.json
```

`Capture` принимает команду немедленно; файл появляется позже. `/status.json`
показывает `busy` и `last_job.state`: `capturing`, `done` или `error`.
`--camera mock` не требует gPhoto2, FFmpeg, v4l-utils или pip. Снимки явно маркированы
DEMO / NO CAMERA; метаданные содержат `simulated: true` / `Simulated: true`.

## Структура

- `linux_digicamcontrol.py`: CLI, Controller, HTTP-маршруты, проверка локальных загрузок.
- `cameras.py`: обнаружение устройств, gPhoto2/V4L2/mock, тайм-ауты и отмена subprocess.
- `web/reelme-test.html`: тестовая страница; один ручной запуск = ровно три кадра.
- `web/liveview.html`: локальный просмотр V4L2 Live View, без создания снимков.
- `fixtures/demo.jpg`: собственное синтетическое изображение, не фотография человека.
- `tests/test_server.py`: стандартный unittest без pip.
- `tests/browser_smoke.py`: дополнительный Playwright-тест; не зависимость сервера.
- `data/session-…/`: создаётся при запуске; JPEG, `session.json`, `server.log`, `.work/`.

## HTTP-контракт

| Запрос | Результат |
|---|---|
| `GET /?CMD=Capture` | `200`, текст `OK`, заголовок `X-Capture-Id`; асинхронная съёмка |
| `GET /?slc=capture&param1=&param2=` | То же |
| `GET /filelist.json` | Массив завершённых фотографий текущего процесса/сессии |
| `GET /image/<имя>.jpg` | Полные байты JPEG, `image/jpeg` |
| `GET /?slc=get&param1=lastcaptured&param2=` | `-` во время съёмки; потом basename файла; пусто до первого кадра |
| `GET /session.json` | `Name`, `Folder`, `Files`, дополнительный объект `Bridge` |
| `GET /preview.jpg` | Последний готовый снимок; не Live View |
| `GET /liveview.html?CMD=LiveViewWnd_Show` | Запуск Live View V4L2; `OK` после первого кадра |
| `GET /liveview.jpg` | Последний свежий JPEG из потока, `no-store`; без записи на диск |
| `GET /?CMD=LiveView_Capture` | Асинхронное сохранение следующего кадра; тот же filelist/Original |
| `GET /liveview.html?CMD=LiveViewWnd_Hide` | Остановка потока и освобождение камеры; Close — синоним |
| `GET /liveview.html` | Локальная страница просмотра/остановки Live View |
| `GET /health`, `GET /status.json` | **Расширение Linux-сервера**, состояние и описание выбранной камеры |
| `POST /test-upload` | **Расширение Linux-сервера**, проверка локальной загрузки |
| `GET /`, `GET /reelme-test.html` | Тестовая HTML-страница |

Регистр `CMD`/`slc` и их значений нечувствителен. Названия полей JSON сохраняются.
Объект фотографии содержит `FileName`, `Name`, `Original`, `Width`, `Height`,
`Size`, `Sha256`, `CapturedAt`, `JobId`, `Simulated`. `Original` — относительный
путь `/image/<имя>`, именно его использует существующая страница ReelMe.
Размеры — из JPEG SOF, без применения EXIF Orientation. Отображение проверяет браузер.

На занятость: `409`, без очереди и без второго спуска. Неподдерживаемые команды,
включая Live View для gPhoto2/mock и изменение настроек камеры, возвращают `501`.
Live View без свежего кадра/при сбое возвращает `503`, не подменяется последним снимком.
Запуск/остановка во время незавершённого capture возвращает `409`.
`HEAD` не вызывает съёмку. Ошибки HTTP возвращаются как JSON `{"error":"..."}`.
Асинхронные ошибки камеры — в `status.json` и журнале, файл при этом не публикуется.
Ответ `OK` не означает, что фотография уже готова. Имена файлов уникальны.
Автоматически повторять команду спуска после сетевого тайм-аута нельзя: первая
команда могла сработать. Сначала проверяется статус/список файлов.

`POST /test-upload` принимает `multipart/form-data`, 1–6 файлов в полях `photos`,
не более 96 МиБ всего и 64 МиБ на JPEG. Требуется Content-Length; chunked не поддержан.
Возвращает `ok`, `files[]` с `name/size/sha256/width/height`, `bytes_received`,
`stored:false`, `local_only:true`. Файлы разбираются в памяти, не пишутся на диск
и никуда не пересылаются. Это настоящий локальный HTTP POST, **не проверка облачного
сервера, его авторизации или CORS**. Не используйте этот endpoint как облачное хранилище.

В комплектной странице эти расширения используются только после распознавания
`app == "linux_digiCamControl"` через `/health`. При `features.live_view` живое
превью включается на время ручного теста внутри `#stage`, capture использует
`LiveView_Capture`. Превью и оригинальный снимок имеют отдельные img/Blob:
оригинал показывается 0,5 с без зеркалирования и не заменяется асинхронным preview.
При ошибке preview оно отключается между экспозициями, без повторного затвора;
сохранённые снимки не очищаются. Завершение/pagehide прекращает polling и освобождает
preview Blob и камеру. Без Linux-расширений страница остаётся
совместима с базовыми маршрутами digiCamControl и проверяет только упаковку файлов.

## Захват и эксплуатация

Одна выбранная камера на процесс. Выбор — интерактивное меню, ID или номер из `list`.
Прямые ID: `gphoto2:usb:001,007`, `v4l2:/dev/video0`, `/dev/video0`, `mock`.
V4L2 также принимает существующий `/dev/v4l/by-id/...`; такой ID удобнее при смене
номеров `/dev/videoN`. Для смены камеры требуется перезапуск, UI переключения нет.

gPhoto2 вызывается с `--port`, `--keep`, `--filename capture-%03n.%C`,
`--capture-image-and-download`. Сервер не удаляет изображения с камеры и не изменяет
настройки экспозиции, USB-драйверы или конфигурацию пользователя. Для одного HTTP
запроса нужна одна JPEG-фотография; RAW-only и серия/брекетинг не поддержаны.
Скачанный RAW и неполные файлы остаются в `.work/<job_id>/` для диагностики.
Поддержка конкретной камеры определяется установленной libgphoto2, а не только USB.

Без Live View веб-камера открывается FFmpeg отдельно для каждой фотографии.
При Live View один FFmpeg владеет камерой, публикуя только последний JPEG в памяти;
Capture ждёт кадр новее команды и сохраняет его через обычный pipeline.
Пропускаются первые 0,7 секунды после открытия (`--warmup`). После warmup PTS
потока вычисляются по номеру кадра и номинальной частоте: повторяющиеся временные
метки UVC не должны завершать MJPEG encoder. Настройки автофокуса
и автоэкспозиции драйвера не меняются. Это не гарантирует резкости/экспозиции за 0,7 с.
Live View останавливается при Hide/Close, shutdown или 15 сек без запросов
preview/capture. Клиент ReelMe не посылает stop при уходе; idle timeout освобождает
устройство. После idle обычная съёмка остаётся доступной. При обрыве/зависании потока
старый кадр не выдаётся, автоматического перезапуска нет: нужен явный Show или Stop.
JPEG веб-камеры кодируется FFmpeg; JPEG DSLR передаётся без перекодирования.
`--size`, `--fps`, `--input-format` применяются только к веб-камерам. При заданном `--size`
фактический размер JPEG проверяется; несовпадение становится ошибкой. Частоту/формат
согласует драйвер. Вывод FFmpeg доступен в журнале.

`--capture-timeout` по умолчанию 25 с. Комплектная страница ожидает файл до 30 с;
при существенном увеличении тайм-аута сервера нужно согласовать тайм-аут клиента.
`Ctrl+C`/SIGTERM останавливает worker и группу subprocess. Частичные файлы не выдаются.
Один lock сериализует съёмку; HTTP-потоки обслуживают опрос одновременно с worker.
Публикация JPEG — атомарный rename; массив содержит только завершённые файлы.

Каждый запуск создаёт новую сессию; прежние файлы сохраняются, но не входят в новый
`filelist.json`. Автоочистки нет: тестовые фотографии содержат персональные данные,
поэтому хранение и удаление после теста остаются ответственностью владельца.
Текущий backend может не обнаружить отключение до следующей команды: `/health`
означает доступность сервера, а не подтверждённое непрерывное присутствие камеры.

## Origin и безопасность

Страница открывается **через этот сервер**, не `file://` и не с другого dev-порта.
Относительные запросы к API имеют один origin: CORS не нужен для этих запросов.
Статика — только из `web/` или явно заданного `--web-root`; directory listing нет.
Запрещены обход путей и выходящие за web-root симлинки.

Привязка жёстко ограничена `127.0.0.1`; параметра публикации в LAN нет. Проверяются
Host, Origin, Referer, Sec-Fetch-Site. Это уменьшает риск cross-site вызова Capture
и DNS rebinding; это не аутентификация против других локальных процессов.
Никаких wildcard CORS, изменений firewall, root-запуска, скрытых облачных запросов
или отключения защиты браузера. На одном origin `localhost` и `127.0.0.1` не смешиваются.
Сервер stdlib предназначен для локальной разработки, не интернет-публикации.

Не завершайте автоматически чужие процессы камеры и не меняйте постоянные udev/ACL
правила без согласования. При занятости дайте пользователю закрыть приложение,
которое держит камеру; при ошибках прав сначала исследуйте конкретный device/ACL.

## Проверки при изменениях

```bash
python3 -m unittest discover -s tests -v
python3 -m py_compile linux_digicamcontrol.py cameras.py
# Дополнительно, в среде с Playwright и Chromium:
python3 tests/browser_smoke.py
```

Сохраняйте совместимость `Capture → filelist → Original`, ручной повтор прогона,
защиту от двух спусков одновременно и явную маркировку mock. Не заменяйте ошибки
успешным ответом и не делайте fallback на mock при сбое физической камеры.
Реальные DSLR и V4L2-устройство требуют отдельной аппаратной проверки.
