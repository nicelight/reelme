# Ожидание запросов и ресурсов

Наблюдения по коду и решения после обсуждения 2026-11-17. Зависания на целевом VPS не измерялись.

## Исправлено: 1. Ожидание API в результатах и съёмке

GET `/display/today`, создание сессии, чтение её состояния и finalize ограничены 15 секундами; передача одного JPEG — 120 секундами при лимите файла 20 MiB. Deadline включает чтение тела ответа и сохраняет отмену при unmount. Экран результатов продолжает существующий polling после ошибки. В съёмке остаётся ручной повтор с тем же `startRequestId`, сохранёнными Blobs и проверкой уже принятых позиций; автоматического повтора операций нет.

Код: `src/client/cloud/Display.svelte`, `src/client/capture/App.svelte`, `src/client/capture/PhotoSession.svelte`. Другие API-запросы этим исправлением не менялись; предзагрузка описана отдельно ниже.

Проверки: `npm run check` и `npm run build` — PASS. Chromium с реальными HTTP streams и ускоренными deadline: зависание до headers и посреди JSON; восстановление Display; ручной повтор старта с тем же ID; потерянные ответы уже принятых upload/finalize без повторных writes; отмена при unmount — PASS. Камера и серверные состояния этой проверки моделировались. Existing `capture.spec.ts` и `transfer.spec.ts` не дошли до сценариев: fixture подключилась к чужому процессу на занятом порту 3197 и получила 403 при login. Чужой процесс не остановлен, fixtures не изменены.

## Исправлено: 2. Готовность карточки и ограниченная предзагрузка

Новые результаты публикуются как ready после проверки видео/кадра и записи PNG QR с тем же receive-токеном, который сохраняется в финальной транзакции. Старые ready без QR-файла сохраняют прежнюю выдачу QR по запросу; миграция БД не требуется.

На клиенте окно загрузки кадра и QR — две попытки до 3 секунд каждая, без паузы. Первое неудачное окно переводит карточку в локальное `delayed` и конец порядка допуска к показу. После допуска/исключения предшествующих карточек она получает второе окно до 6 секунд. Второй отказ переводит её в `deprecated`, исключает из будущих очередей и выводит номер с текстом «пройдите фотосессию снова» в верхних статусах по существующим правилам восьми слотов. Начальные карточки после восстановления не вылупляются заново; текущий перенос центра завершается без вмешательства.

На terminal-переход отправляется один authenticated запрос записи предупреждения `DISPLAY_CARD_DEPRECATED` в Pino. Запись best-effort: при недоступности сервера не повторяется и не блокирует показ. Серверное видео/ready/архив не изменяются. Перезагрузка сбрасывает локальные состояния. Подробные правила: `.memory-bank/states/results-display.md`, endpoint — `.memory-bank/contracts/http-api.md`.

Проверки: `npm run check`, `npm run build`, выбранные server/shared tests — PASS.
Проверены запись и содержимое QR до ready, отказ публикации при ошибке записи,
восстановление, legacy QR, права/содержимое записи лога, cleanup, real/simulated
generation и email. Шесть Chromium-сценариев — PASS: delayed и восстановление
initial без hatch, два исчерпанных окна и единственный log, поздние ответы,
unmount, несколько delayed без взаимного ожидания, смена даты и прежнее
восстановление stage. В state-тесте отдельно проверена поздняя initial-карточка
во время переноса центра. Browser API/сеть моделировались; VPS/fal не проверялись.

## Исправлено: опрос статуса email

В текущем рабочем дереве опросы формы получения письма выполняются последовательно; зависший GET отменяется по таймауту 15 секунд, после чего опрос возобновляется. Состояние `sent` прекращает опрос; unmount отменяет текущий GET и дальнейшие обращения.

Код: `src/client/cloud/Receive.svelte`.

Проверено в Chromium через Vite с управляемыми ответами API: медленный GET не порождает второй; после таймаута следующий опрос получает `sent`; после `sent` и unmount новые опросы не запускаются. Это локальная симуляция, не проверка SMTP или VPS.

Наложение опросов email и согласованные таймауты API исправлены и проверены локально. Поведение предзагрузки согласовано и описано выше. Последовательный обработчик генераций не меняем.
