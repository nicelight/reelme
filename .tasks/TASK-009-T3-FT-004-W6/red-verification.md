# TASK-009 — независимая семантическая проверка

2026-11-14. SEMANTIC_VERDICT: semantic-fail.

## Подтверждённая находка

**R1 — mailbox quota ошибочно запускает автоматический fallback.**
В `src/server/sessions/email.ts:37` ветка `mail` совпадает с `mailbox`, а проверка
текста не исключает явный enhanced status `5.2.2`. Поэтому ответ после DATA
`552 5.2.2 Mailbox size limit exceeded` считается отказом вложения.

Воспроизведено настоящим Nodemailer через `tests/email-smtp.ts`, без прямого
изменения состояния delivery:

1. Создать синтетическую ready-сессию через `preparedSession`/`publishReady`.
2. Установить `smtp.setAction(async () => '552 5.2.2 Mailbox size limit exceeded')`.
3. Подтвердить адрес через `POST /api/receive/<receive_token>/email`.
4. Выполнить `worker.runOnce()`, считая обращения к `transport.sendMail`.
5. Получены **2** обращения: MP4, затем письмо без вложения. Итог `failed`.
   Повторный `runOnce()` новых обращений не делает.

Ожидалось **1** обращение и `failed`: квота ящика не является явным отказом файла
или размера письма. Нарушается ограничение TASK-009 о fallback только по причине
вложения и [контракт интеграции](../../.memory-bank/contracts/integrations.md#почта-smtpbz).
Доказательство: [red-independent.log](red-independent.log), строка JSON с
`expectedAttempts:1, actualAttempts:2`. Подтверждённый эффект ограничен лишней
автоматической SMTP-попыткой; доставленный дубль и потеря данных не наблюдались.

Полезная коррекция: исключить явно указанные причины отказа, не относящиеся к
вложению, из текстовой эвристики; добавить этот вариант ответа к существующей
SMTP-проверке. После коррекции достаточно targeted повторного прогона.

письма. Эта коррекция соответствует исходному ограничению; новых существенных
нарушений в изменённой классификации не найдено.
