# Данные ReelMe

Правила настройки и совместимости: [матрица](../../docs/slot-setup/matrix.md),
[план внедрения](../analysis/slot-setup-plan.md). Состояние реализации и проверки —
в [задачах](../tasks/index.json); правила legacy ниже относятся только к старым записям.

Основание — [PRD](../prd.md). Дата, номер и снимок сюжета фиксируются при начале съёмки.
Ниже минимальная техническая модель; [состояния](../states/lifecycle-map.md) описаны отдельно.

## Записи и владельцы

| Запись | Данные |
|---|---|
| Слот | ID, видимость, описание, модель, параметры, промпт и материалы |
| Мероприятие | Дата Новосибирска, название, диапазон участников (nullable), локация, завершённость настройки, следующий номер посетителя, состояние удаления |
| Фотосессия | ID, ключ повтора старта, дата/номер, снимок сюжета, фото, состояние генерации, fal ID/URL, результат, состояние email и времена выдачи |
| Медиа | ID/путь, тип, размер, владелец и назначение; у фото посетителя — индекс позы |

Scenarios отвечает за слоты и их материалы; Sessions — за фотосессии, мероприятия,
результаты и почту. Для email достаточно текущего адреса, состояния и ошибки в сессии;
отдельный журнал всех попыток не нужен. Данные хранятся в SQLite, байты файлов — на VPS.

## Начало съёмки и идентичность

После «Мне нравится» сервер проверяет слот и создаёт сессию со снимком настроек,
датой и номером в одной короткой транзакции. Номер уникален внутри даты.
Повтор старта с тем же ключом возвращает существующую сессию; отдельный реестр ключей
после удаления сессий не ведётся. Переход суток и повтор загрузки дату/номер не меняют.
Номер показывается посетителю после приёма всех фото. Пропуски номеров допустимы.

`events.name`, `participant_range`, `location`, `setup_complete` хранят данные первой
съёмки дня. Настройка мероприятия и первая фотосессия фиксируются одной транзакцией;
повтор `startRequestId` возвращает исходную сессию без повторной записи полей.
`event_name_counter` выдаёт следующий N для `Session_N` и не очищается вместе с
мероприятием. Сохранение ручного названия тоже резервирует порядковый номер дня.
Skip оставляет диапазон участников NULL, локацию «Новосибирск». Последующие старты
не меняют метаданные. Админский тест создаёт день с незавершённой настройкой.
Миграция сохраняет старые сессии, назначает старым дням `Session_N` по порядку дат;
если в дне уже была обычная съёмка, настройка считается завершённой.

## Снимок слота и фото

Снимок содержит описание, миниатюру, модель, параметры, промпт, конкретный план
съёмки и ссылки на материалы. Правка слота влияет только на новые сессии.
Заменённый файл получает новый путь; прежний сохраняется, пока нужен слоту или сессии.
Проверка использования материалов опирается на сохранённые ссылки; отдельный протокол
закрепления/освобождения и система версий слотов не требуются. Демо P2V не отправляется в fal.

Форма снимка — `SlotSnapshot` в [capture.ts](../../src/shared/capture.ts):
параметры и входы генерации находятся в `generation`; описание, миниатюра и
`demoId` — отдельно. Новый `posePlan` содержит позиции `index`, `participant`,
`guideNumber`, инструкцию и необязательные `guideMediaId` и `caption`; `expectedPhotos` равен
длине плана (до восьми). У двух людей последовательные равные наборы; группа —
один набор с пятым образцом. План не перестраивается при чтении сессии.
Отсутствие `posePlan` обозначает legacy: прежние 1/4 фото и старые позы/входы моделей.
Raw-слот без setup запускается прежним путём до первого нового сохранения;
редакторские defaults не мигрируют запись автоматически.
SQLite хранит начальные записи в `events` и `capture_sessions`; уникальны
`start_request_id` и пара `(event_date, number)`. Создание события, выдача номера
и запись снимка выполняются одной транзакцией; повтор читает сохранённую запись.

`capture_photos` хранит уникальную пару `(session_id, pose_index)`, относительный
путь, размер и размеры изображения. SQLite допускает позиции 0..7; сохраняющая
миграция прежнего предела 0..3 удерживает фотографии и FK/токены `provider_media`.
Приём дополнительно ограничен конкретным планом сессии. Байты находятся в
`DATA_DIR/media/sessions/<sessionId>/<uuid>.jpg`. Каждая попытка получает новый
путь; после проверки файла короткая транзакция повторно проверяет `capturing`
и заменяет одну позицию. Прежний файл удаляется после успешной замены.
Так незавершённая загрузка не перезаписывает фото, уже принятое finalize.

Фото сохраняются по sessionId и индексу позы. При повторе неудавшейся загрузки клиент
передаёт тот же кадр в ту же позицию; другие кадры сохраняются. После завершения приёма
фотографии не меняются. Принадлежность JPEG текущему посетителю проверяет адаптер камеры.

## Исходники и образцы поз

`slot_media.template_slot_id` и `template_orientation` фиксируют принадлежность
импортированного исходника. Это metadata существующего media storage, без реестра
версий. Новый импорт всегда получает новый ID/путь. Ранее закреплённый за тем же
слотом upload без provenance остаётся допустимым, если совместим с настройками.
Новый слот не может принять произвольный upload вместо именованного исходника.

`capture_guides` хранит изображения и подписи пяти ракурсов. При старте
Scenarios копирует guideMediaId и caption в соответствующие позиции snapshot. Изменение назначения
не меняет начатую сессию. Cleanup удерживает текущие назначения и все IDs из живых
snapshots; образцы не передаются в provider payload.

## Тестовые настройки и времена генерации

`simulateGeneration: boolean` по умолчанию false; отсутствие поля в старой
записи/snapshot означает реальный путь. Необязательный `simulationOutput: "video"`
допустим только вместе с true и включает полную выдачу локального тестового MP4;
true без output сохраняет прежний input-only смысл. Worker читает только snapshot.
Оба поля хранятся в существующем JSON, миграция таблиц не требуется. Тестовый ready
не входит в выбор последнего реального видео; архив возвращает `testVideo: true`.
Новый `testPhotoIds` содержит активный набор media IDs в порядке `posePlan`;
legacy использует `testPhotoId`. Эти поля не входят в generation или обычный snapshot.
Manual snapshot отдельно сохраняет свои источники для повтора после потери ответа.
Каталог и provider payload тестовые настройки не раскрывают.

Каждый тестовый JPEG — проверенный immutable материал Scenarios. Новый тест копирует
свой JPEG в каждую позицию Sessions; один файл не размножается на весь новый план.
Незавершённый legacy-тест сохраняет прежний однокадровый источник. Замена материалов
слота не меняет уже зафиксированный набор. Очистка учитывает все `testPhotoIds`
текущего слота и сохранённых manual snapshots, сохраняя материалы других сессий.

Редактор кеширует назначения по человеку/ракурсу, у группы — по номеру кадра;
групповые и индивидуальные назначения раздельны. Кеш переживает смену setup,
но серверу передаётся только активный набор. Байты JPEG/base64 не хранятся в
Web Storage; восстановление тестового кеша после закрытия браузера не требуется.

`generation_jobs` дополняется nullable `submitted_at` и `ready_at` (UTC epoch ms).
`submitted_at` записывается непосредственно перед фактической попыткой submit в fal;
при повторе без подтверждённого ID это время обновляется. После подтверждения ID
опрос/скачивание/рестарт его не меняют. `ready_at` фиксируется при первом переходе
в ready; повтор публикации его не сдвигает. Для симуляции оба поля остаются NULL.
Миграция сохраняет существующие строки/файлы; старым результатам времена не выдумываются.

Последнее видео выбирается среди ready-сессий данного slot_id в неудаляемых
мероприятиях: `COALESCE(ready_at, created_at)` по убыванию, затем created_at/id.
Для старых записей created_at служит лишь запасным порядком, не временем готовности.
`elapsedMs = ready_at - submitted_at` возвращается только при обоих корректных временах;
иначе NULL. Новая pending/failed/simulated-сессия не вытесняет прежний ready-результат.

## Владение файлами

Фото посетителя, готовое видео и кадр результата принадлежат сессии. Их размеры формируют
объём мероприятия; общие материалы слота не прибавляются для каждого посетителя.
Удаление мероприятия удаляет его собственные файлы, сохраняя используемые материалы слотов.
Архив и ручное удаление доступны только для прошедших дней.

Файл сначала записывается и проверяется, затем отмечается готовым в БД. Сетевые вызовы
и запись больших файлов не выполняются внутри SQL-транзакций. Уборка непредвиденных
остатков после аварии не оформляется в отдельную подсистему первой версии.

## Доступ и выдача

Ссылки формы и скачивания относятся к конкретной сессии; номер посетителя не является
секретом доступа. Аккаунты и ключ установки имеют отдельные права согласно PRD.
В сессии сохраняются открытие формы, первое подтверждение email, состояние отправки
и ошибка. Трёхминутный срок не продлевается при повторе. Полный email не попадает на общий экран.
