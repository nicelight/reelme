# Архитектура ReelMe

## Основание и готовность

[PRD](../prd.md), [REQ/AC](../requirements.md) и [принципы](../constitution.md) задают поведение.
Файлы продукта ещё не реализованы. Стек и размещение данных приняты; почтовый сервис
и схема авторизации ещё уточняются. Контракты и состояния разрабатываются до задач реализации.

## Architecture Spine

### AD-001 — Локальный origin съёмочного интерфейса
- Rule: `reelme.html` обслуживает digiCamControl по `http://localhost:5513/reelme.html`.
  Загружаемые с облака скрипты работают в этом origin и обращаются к локальному API камеры.
  Админка, промоэкран и форма выдачи обслуживаются нашим сервером.
- Binds: сборка/доставка клиентского кода, CORS облачного API, установка Windows.
- Prevents: попытку обращаться к камере из облачного origin без согласованного локального посредника.
- Verification: испытание страницы, JPEG и Live View на целевой Windows/Canon.
- Source: [REQ-016/017](../requirements.md), [размещение](../prd.md#принятая-схема-размещения).

### AD-002 — fal выполняет тяжёлую генерацию
- Rule: сервер ReelMe хранит и передаёт материалы, управляет заданиями и выдачей;
  модели выполняются на fal. Все согласованные модели обязательны.
- Binds: модельные адаптеры, владение запросом и результатом, ресурсы VPS.
- Verification: [FT-003](../features/FT-003-video-generation.md#acceptance-criteria).
- Source: [генерация](../prd.md#фоновая-генерация), [схемы fal](../analysis/fal-api.md).

### AD-003 — Подтверждённый запрос наблюдается по ID
- Rule: повтор submit допустим только без подтверждения. Полученный `request_id`
  сохраняется; последующие действия относятся к нему. Встроенные повторы fal включены.
  Дубль при потерянном подтверждении допустим, отдельная защита от него не требуется.
- Binds: обработчик генерации и восстановление после сетевых ошибок.
- Verification: [FT-003-AC-003](../features/FT-003-video-generation.md#ft-003-ac-003).
- Source: принятое правило [PRD](../prd.md#фоновая-генерация).

### AD-004 — Генерация и выдача имеют разные завершения
- Rule: готовый файл, ссылка и форма завершают генерацию. Открытие QR, письмо,
  исчезновение с публичного экрана и удаление мероприятия не удаляют историю преждевременно.
- Binds: модель состояния сессии, почтовая обработка, публичная проекция и очистка.
- Verification: [FT-003-AC-004](../features/FT-003-video-generation.md#ft-003-ac-004),
  [FT-004-AC-004](../features/FT-004-public-delivery.md#ft-004-ac-004).
- Source: [PRD](../prd.md#получение-по-email).

### AD-005 — Caddy на входе VPS
- Rule: входящий HTTP/HTTPS-трафик домена `reelme.natureonzoom.win` принимает Caddy.
  Его конфигурация распределяет запросы между статическими файлами и серверным API.
- Binds: развёртывание, TLS, раздача клиентской сборки и проксирование API.
- Verification: HTTPS-проверка домена, статики и маршрута к backend на целевом VPS.
- Source: прямое решение оператора; [Caddy reverse proxy](https://caddyserver.com/docs/quick-starts/reverse-proxy),
  [Automatic HTTPS](https://caddyserver.com/docs/automatic-https).

### AD-006 — Svelte 5 для интерфейсов
- Rule: интерфейсы ReelMe реализуются на Svelte 5. Съёмочный интерфейс монтируется
  в локальной странице и сохраняет её origin согласно AD-001.
- Binds: клиентская реализация и сборка экранов.
- Verification: сборка Svelte и запуск локального и облачных интерфейсов.
- Source: прямое решение оператора; [Svelte mount](https://svelte.dev/docs/svelte/imperative-component-api).

### AD-007 — TypeScript, Node.js / Fastify и SQLite
- Rule: основная реализация — TypeScript. HTTP API работает на Node.js / Fastify;
  постоянные записи хранятся в SQLite на этой же VPS. Видео и фото находятся на диске,
  в БД хранятся их метаданные и пути.
- Binds: серверная реализация, транзакции, миграции, обработка файлов и развёртывание.
- Verification: запуск приложения с локальной SQLite, сохранение данных и восстановление
  обработки после перезапуска; схема БД не содержит медиабайты.
- Source: прямые решения оператора о стеке и хранении медиа на VPS.

## Серверная основа

Единое приложение с функциональными модулями. Сервер — TypeScript / Node.js / Fastify;
экраны — Svelte 5; для сборки предлагается Vite. Данные — SQLite на локальном диске той же VPS.
Fastify работает за Caddy и направляет API-запросы прикладным обработчикам ReelMe.
Фото/видео хранятся файлами на VPS; объём диска зависит от посещаемости
и фактических размеров. Каталог данных находится отдельно от заменяемой сборки приложения.

Один серверный процесс обслуживает HTTP и фоновые задачи через асинхронные операции.
Состояние фоновой работы хранится в БД. Ожидание fal не удерживает HTTP-запрос посетителя;
после перезапуска обработчик возобновляет наблюдение за сохранёнными ID.
Внешняя отправка email использует отдельного почтового провайдера, который ещё не выбран.

| Часть | Ответственность |
|---|---|
| Caddy | Входящий HTTPS, статические файлы и проксирование серверного API |
| Локальный интерфейс съёмки | Каталог, позы, управление камерой, передача фото, показ номера |
| Облачные интерфейсы | Управление слотами/мероприятиями, публичные карточки и прогресс, форма email |
| Сервер ReelMe | Авторизация, сессии, модельные запросы, подготовка файлов, email и очистка |
| Постоянные данные | Слоты, сессии и события обработки, номера по датам, ссылки и размеры файлов |
| Медиа | Материалы слотов, фото сессий и результаты; у каждого файла определён владелец и срок |
| fal.ai / почтовый сервис | Внешние вычисления и доставка писем с подтверждаемым результатом обращения |

Подробные внутренние модули и разрешённые зависимости определяются в
[Boundary Map](../contracts/boundary-map.md). Таблица выше —
крупные части системы, не принятый граф модулей.

## Поток данных

1. Администратор сохраняет слот и материалы. Клиентский каталог читает только видимые слоты.
2. Локальный интерфейс снимает фотографии и передаёт серверу сессию выбранного сюжета.
3. Сервер связывает сессию с мероприятием по `Asia/Novosibirsk` и ежедневным номером.
4. Обработчик собирает модельный запрос из материалов сессии и сохранённых URL слота.
5. После получения fal ID обработчик наблюдает запрос, затем сохраняет и проверяет видео.
6. Публичная карточка ведёт в форму этой сессии; подтверждение email запускает отправку письма
   и трёхминутный срок публичного показа.
7. Админка сохраняет доступ к результатам до ручного либо автоматического удаления мероприятия.

Момент закрепления даты/номера, снимок параметров слота, порядок фиксации БД/файлов
и восстановление незавершённых операций описываются в предметных спецификациях до задач.

## Обоснование и пределы

- Один сервер и одна установка не требуют распределённой БД. SQLite применим к серверному
  приложению, когда БД находится на том же сервере; WAL позволяет чтению и записи
  идти параллельно, но одновременно пишет один writer. Поэтому сетевые вызовы и
  обработку медиа нельзя держать внутри транзакций.
  [SQLite: применение](https://www.sqlite.org/whentouse.html),
  [WAL](https://www.sqlite.org/wal.html).
- Общий TypeScript позволяет описать разделяемые структуры API для сервера и интерфейсов.
  Fastify поддерживает типизацию обработчиков.
  [Fastify TypeScript](https://fastify.dev/docs/latest/Reference/TypeScript/).
- Vite выпускает статические assets и manifest; стабильный локальный загрузчик сможет
  получать актуальную сборку с облака. Точные URL, CORS и политика обновления требуют
  отдельного контракта, а не предположения, что пути облачного HTML сработают локально.
  [Vite backend integration](https://vite.dev/guide/backend-integration).

Производительность на VPS 4 ГБ не измерялась. Диск рассчитывается отдельно от RAM;
принятая посещаемость — 100 посетителей в день мероприятия. При ежедневной работе
за 14 дней это ориентировочно 1400 сессий; точный максимум зависит от границы автоочистки.
Размер диска рассчитывается по измеренным размерам фото/видео с запасом под материалы
слотов и эксплуатацию. Почтовый сервис и схема авторизации ещё не выбраны.
