# HTTP API ReelMe

Правила настройки и совместимости: [матрица](../../docs/slot-setup/matrix.md),
[план внедрения](../analysis/slot-setup-plan.md). Состояние реализации и проверки —
в [задачах](../tasks/index.json); правила legacy ниже относятся только к старым записям.

Контракты API по [PRD](../prd.md); реализованный объём и проверки — в [задачах](../tasks/index.json).
Префикс — /api, кроме страницы QR и скачивания. [Права](access.md) проверяет сервер.
Ошибки содержат code/message без секретов и внутренних ответов провайдера.

## Каталог и слоты

| Операция | Доступ | Данные |
|---|---|---|
| GET /public/catalog?page=1 | Без аккаунта | Та же безопасная проекция видимых сюжетов, по 12 на страницу |
| GET /public/catalog/:id/media/:mediaId | Без аккаунта | Только текущая обложка/превью видимого сюжета; Range |
| GET /catalog?page=1, /catalog/:id | Установка | Видимые сюжеты, по 12 на страницу; описание, миниатюра, пример видео |
| GET /catalog/:id/media/:mediaId | Установка | Только миниатюра или пример видео текущего видимого сюжета; байты с Range |
| GET /admin/slots, /admin/slots/:id | Администратор | Список и полная конфигурация слота |
| GET /admin/slots/:id/prompt-history | Администратор | До 10 последних уникальных записей `{model, prompt}` сохранённого слота, новые первыми |
| POST /admin/slot-media | Администратор | Multipart `file` → метаданные с `id` материала |
| GET /admin/slot-media/:id, /admin/slot-media/:id/info | Администратор | Байты (с Range) / метаданные материала. Для изображений браузер проверяет приватный кеш по ETag после авторизации |

| DELETE /admin/slots/:id | Администратор + разрешённый Origin | После подтверждения в карточке сюжет исчезает из редактора и каталога. Начатые сессии и материалы их snapshots сохраняются |
| PATCH /admin/slots/:id/visibility | Администратор + разрешённый Origin | `{visible: boolean}` → 204. Меняет видимость в сохранённой конфигурации, в том числе у старых сюжетов |
| POST /admin/slots/:id/template-video | Admin + разрешённый Origin | JSON `{orientation,model}` для импорта из папки или multipart с MP4 в `file` и query-параметрами `orientation`, `model` для загрузки из браузера. Возвращает immutable `Media`, 201 |
| GET /admin/capture-guides | Администратор | Пять `{number,instruction,mediaId?,caption?}` |
| GET /admin/email-settings | Admin | Активный источник и сохранённые профили с признаком наличия пароля |
| PUT /admin/email-settings | Admin + разрешённый Origin | Сохранить и выбрать профиль. Для mailru передаются provider, user и пароль при первом сохранении. Для smtpbz также host, port, from |
| POST /admin/email-settings/test | Admin + разрешённый Origin | `{profile, to}` → 204 после принятия тестового письма сервисом. Настройки и очередь не меняются |
| GET /admin/capture-settings | Admin | Настройки новых фотосессий |
| PUT /admin/capture-settings | Admin + разрешённый Origin | `startMode` (manual/automatic), `countdownSeconds`, `reviewSeconds`, `receiptSeconds` (целые 1–60), `sendCaptureLogs` (boolean, по умолчанию false), `photoMaxEdge` (0, 1024 или 2048 пикселей по длинной стороне, по умолчанию 0 — полное разрешение), `rotateWebUsb180` (boolean, по умолчанию false, поворот превью и JPEG фотобудки WebUSB) → сохранённые значения |
| PUT /admin/capture-guides/:number | Admin + разрешённый Origin | Обновляет переданные поля `mediaId` (UUID или null) и `caption` (до 120 символов, пустая строка очищает подпись) |

Каталог возвращает `CatalogPage` (`items`, `page`, `pageSize=12`, `total`, `totalPages`),
карточка — `CatalogItem` из [capture.ts](../../src/shared/capture.ts). `previewId`
ссылается на исходник V2V или демо P2V; без демо отсутствует. Вместе с ним
`previewOrientation` передаёт portrait/landscape по сохранённым размерам медиа
(при отсутствии размеров — по настройке слота). Открытие каталога не запускает ffprobe. Скрытый/несуществующий
сюжет и материал вне его текущей публичной карточки возвращают 404. Промпты,
настройки моделей и дополнительные референсы не входят в проекцию каталога.
Пагинация API — транспортная: клиент объединяет все страницы в единую карусель,
пять видимых карточек не ограничивают число доступных сюжетов.

Конфигурация: описание, видимость, миниатюра, режим, модель, параметры и материалы PRD.
Сервер проверяет допустимые входы по [схемам моделей](../analysis/fal-api.md).
Новый Recast принимает необязательный промпт; пустой текст не отправляется.
Демо P2V не входит в генерацию. При старте сессия сохраняет
текущие настройки и конкретные материалы. Отдельного контроля конкурентных редакций нет.
Медиа установки доступны с ключом; публичная промогалерея использует отдельные
read-only `/public/catalog` маршруты. Медиа редактора требуют аккаунт администратора.
Публичного API для начала съёмки или генерации нет.

Форма JSON редактора — `SlotInput` в [scenarios.ts](../../src/shared/scenarios.ts).
Новый setup содержит `participants: 1|2|'group'`, `photosPerParticipant: 1..4`,
`orientation: landscape|portrait` и `aspectRatio` только для поддерживающих его endpoint.
Матрица задаёт допустимые сочетания, качество и остаток дополнительных references;
V2V также принимает references, если это разрешает выбранный вариант.
Сохраняются только поля выбранного режима/модели; неизвестные поля отвергаются.
V2V без `videoId` сохраняется как черновик: он исключён из каталога и не запускается.
При открытии старого слота редактор получает прежние смысловые defaults; сама запись
не переписывается. До первого сохранения нового setup старый слот запускается прежним путём.
Для Recast `recastShotsConfirmed` фиксирует подтверждение администратора о кадрах
≤15 с: ffprobe проверяет общую длительность, но не смысловые границы кадров.
H3 Reference использует `promptExpansionMode: disabled`. Ограничения загрузки
и проверка файлов — в [руководстве](../../docs/MANUAL.md#работа-с-редактором).

Готовые промпты выдаются по `/slot-prompts/` вне API как обычный текст с
`Cache-Control: no-cache`; нулевой файл Recast — успешный ответ. Редактор читает
`response.text()`, различает HTTP-ошибку и пустой текст, игнорирует устаревший
ответ после смены setup или ручной правки. Текст не собирается из частей в runtime.

## Исходники и образцы

Новый UUID слота доступен до первого сохранения. Импорт принимает только UUID,
модель V2V и ориентацию; путь клиента не принимается. Файл
`<slot-id>__landscape.mp4` / `<slot-id>__portrait.mp4` читается из серверной папки
шаблонов и копируется в immutable storage после проверок. Отсутствие —
404 TEMPLATE_VIDEO_MISSING; неверная ориентация/модельные ограничения — 400.
Повторный импорт создаёт новый media ID; слот изменяется только после save.
Плеер использует тот же videoId. Чужой исходник или другая ориентация отвергаются
при save; ранее закреплённый upload того же слота допускается при совместимости.

Образцы загружаются обычным media API как изображения и назначаются номерам 1..5.
PUT с null удаляет текущее назначение. Уже начатые сессии сохраняют прежние IDs;
при отсутствии образца новый snapshot сохраняет его отсутствие. Установка читает
образец по ID из плана через `GET /capture/guides/:mediaId` с ключом установки.
Маршрут выдаёт только назначенные образцы. После замены старый образец доступен по маршруту начатой сессии.

## Тестирование слота

Сохранение слота принимает `simulateGeneration` (boolean, default false),
`simulationOutput?: "video"` (только при true) и
необязательный `testPhotoIds` (UUID[]) в порядке активного плана.
Для нового теста нужен отдельный JPEG на каждую позицию; неполный набор не запускается.
`testPhotoId` используется только для прежних записей/повторов. Тестовые фото
загружаются существующим POST /admin/slot-media; при выборе для этой роли сервер дополнительно требует
JPEG ≤20 MiB/40 MP. Поле редактора явно указывает JPEG и не предлагает видео.
Настройка/fixture доступны только admin; проекция catalog их не возвращает.

| Операция | Доступ | Данные и результат |
|---|---|---|
| POST /admin/slots/:id/test-generations | Admin + разрешённый Origin | `{startRequestId}` UUID → `CaptureStatus`; 201 при первом полном приёме, 200 при повторе |
| GET /admin/slots/:id/sessions/:sessionId | Admin | `CaptureStatus` этого слота, включая simulated и безопасную ошибку |
| GET /admin/slots/:id/latest-video | Admin | `{video: LastSlotVideo|null}` |
| GET /admin/slots/:id/results/:sessionId/video | Admin | Собственный ready MP4 этой сессии/слота, с Range |

Тестовый POST использует сохранённый слот и полный `testPhotoIds`, для legacy —
`testPhotoId`; допускает скрытый слот, но не произвольные параметры/URL/path в body.
При неполном новом наборе — 400 TEST_PHOTOS_REQUIRED; для отсутствующего legacy JPEG —
TEST_PHOTO_REQUIRED, неверный файл — INVALID_PHOTO, без запуска генерации. Один ключ для другого
слота — 409 START_CONFLICT. Повтор не создаёт вторую сессию; незавершённая конкурентная
подготовка — 409 TEST_IN_PROGRESS. При повторе capturing-теста используются fixture
из сохранённого снимка и уже принятые позиции; после finalize копирование запрещено.
Ключ обычной camera-сессии не переиспользуется для ручного теста (409 START_CONFLICT).
Проверка и сохранение фото переиспользуют правила
обычного приёма; долгие файловые операции не выполняются внутри SQL-транзакции.
Результат POST не ждёт fal. Админка опрашивает GET состояния, а не меняет права
существующих installation endpoints. Кнопка недоступна для нового/несохранённого
слота, во время загрузки или собственного незавершённого POST. При потере ответа
сохраняется тот же startRequestId до выяснения исхода; новый осознанный тест — новый ID.

`LastSlotVideo` содержит `sessionId`, `videoUrl`, nullable `submittedAt`, `readyAt`,
`elapsedMs`. Порядок выбора и совместимость старых строк — [данные](../domains/core-domain.md#тестовые-настройки-и-времена-генерации).
Видео URL содержит sessionId, а не меняющийся указатель на последний файл, поэтому
повторные Range-запросы не склеивают разные результаты. Удалённый/чужой slot/session,
не-ready результат или отсутствующий файл — 404. Просмотр не отмечает receive opened
и не выдаёт посетительский/download/provider token. Статус и плеер обновляются при
открытии слота и во время незавершённого теста; последний успех остаётся видимым.

## Съёмка

Все операции требуют ключ установки.

| Операция | Данные и результат |
|---|---|
| POST /capture/sessions | startRequestId, slotId, eventSetup → sessionId, дата, номер, план поз, story и captureSettings из snapshot |
| GET /capture/sessions/:id/thumbnail | Закреплённая картинка сюжета из snapshot, независимо от правок/видимости текущего слота; ключ установки обязателен |
| GET /capture/sessions/:id/guides/:number | Закреплённый образец из snapshot; 404 при отсутствии, ключ установки обязателен |
| GET /capture/sessions/:id | `CaptureStatus`: состояние, принятые позиции, полный набор и подтверждение finalize |
| POST /capture/sessions/:id/cancel | Ключ установки. Подтверждённая смена сценария переводит сессию из `capturing` в `cancelled`. Ответ 204, в том числе при повторе. После передачи на генерацию ответ 409 |
| POST /capture/sessions/:id/transfer | Ключ установки. Начало передачи завершает контроль связи до загрузки первого JPEG. Возвращает текущий `CaptureStatus`, повтор безопасен |
| PUT /capture/sessions/:id/photos/:poseIndex | Multipart `file` (JPEG) → `CaptureStatus` с принятой позицией |
| POST /capture/sessions/:id/heartbeat | Ключ установки, без тела, ответ 204. Сервер отмечает контакт только для новой сессии установки до начала передачи фото. Неизвестная или удаляемая сессия получает 404 |
| POST /capture/sessions/:id/capture-reports | Отчёт попытки или настроек камеры для сессии с включённым сбором. 204 при сохранении и повторной доставке, 409 при выключенном сборе |
| POST /capture/sessions/:id/finalize | Полный набор → `submit_pending`, `CaptureStatus.finalized=true` |

Первый старт возвращает 201, повтор — 200 с тем же `StartReceipt` из
[capture.ts](../../src/shared/capture.ts). `startRequestId` и `slotId` — UUID.
Текущий клиент передаёт `eventSetup: {action:'check'}`. Если настройка дня ещё не
завершена, получает 409 `EVENT_SETUP_REQUIRED` без создания сессии и показывает форму.
`{action:'save',name,participantRange,location}` сохраняет введённые данные;
`{action:'skip'}` сохраняет автоматическое `Session_N`, NULL-диапазон и Новосибирск.
Название после trim — 1–120 символов, локация — 1–160; диапазоны — точные значения
из [events.ts](../../src/shared/events.ts). Настройка и старт атомарны, тот же
`startRequestId` безопасен после потери ответа. Уже настроенный день не переименовывается
следующими стартами. Отсутствие `eventSetup` сохраняет прежний протокол старых клиентов:
обычный старт создаёт автоматическое мероприятие и считает настройку завершённой.
Повтор одного ключа для другого слота даёт 409; для того же слота возвращается
сохранённая сессия, даже после скрытия слота или смены суток. Проверка текущей
видимости выполняется перед первым стартом. Номер в ответе API ещё не показывается
посетителю; клиент хранит результат и план поз для съёмки/передачи.
Дата, номер и план сохраняются; `state` в повторном ответе отражает актуальное состояние.
StartReceipt и CaptureStatus содержат `story: {slotId, description, thumbnailId}` из snapshot;
клиент допускает отсутствие поля в ранее сохранённых receipts и обновляет его через статус.
Обложка использует адрес каталога с закреплённым thumbnailId. При 404 или отсутствии slotId клиент берёт изображение по маршруту сессии.
Браузер повторно использует файлы по тем же адресам между сессиями. После загрузки обложки и текущей позы клиент по очереди подгружает остальные уникальные образцы плана с низким приоритетом.

`CaptureStatus` из [capture.ts](../../src/shared/capture.ts) содержит sessionId,
дату, номер, исходный план и state, а также `acceptedPoseIndices` (индексы с нуля).
Новый план содержит участника, номер образца и конкретные позиции до индекса 7;
приём проверяет принадлежность позиции сохранённому плану. Статус включает
`complete` (полный набор на сервере) и `finalized` (набор передан на обработку).
Полный, но ещё не финализированный набор не разрешает показ номера. GET/PUT/finalize
возвращают 200; неполный finalize и запись после finalize — 409. Неверный JPEG
или индекс — 400, неизвестная сессия — 404, превышение 20 MiB — 413.
Принимается один JPEG в multipart-поле `file`, до 40 мегапикселей; проверяется
декодирование, оригинальные байты сохраняются без преобразования.

Повтор старта возвращает существующую сессию по ключу запроса. После удаления отдельный
реестр старых ключей не сохраняется. Загрузка адресует конкретную позицию; до finalize
повтор записывает тот же кадр в неё, не затрагивая остальные. После finalize фото закрыты
для изменений. Сервер проверяет JPEG и количество фото, но не ведёт протокол сравнения hash.
Клиент начинает PUT/finalize после ручного завершения или по таймеру просмотра серии; пересъёмки до него локальны.
Повтор finalize возвращает текущее состояние без нового перехода в обработку.
После подтверждения finalize установка показывает номер. Повторные запросы
обложки и образцов фотосессии и изображений доступных карточек /display
поддерживают ETag и приватную проверку кэша после проверки прав.
`submit_pending` в SQLite — граница FT-003; потребитель генерации реализуется отдельно. Ошибка камеры/загрузки допускает ручной повтор.

| POST /events/:key/finish | Оператор/администратор и разрешённый Origin | Завершает указанное мероприятие сегодня. Повтор возвращает 204, при смене дня — 409 |
| GET /events, /events/:key | Оператор/администратор | Прошедшие мероприятия: date, name, participantRange (nullable), location; размеры списка и сессии галереи |
| GET /events/:key/:id/video-details | Оператор/администратор | Те же Details, что у плеера результатов, для готового ролика указанного архивного мероприятия |
| DELETE /events/:key | Администратор | Удаление прошедшего мероприятия после подтверждения в UI |
| GET /admin/event-preparation | Администратор | Последняя дата удаления включительно, количество подходящих мероприятий и состояние фоновой очистки |
| POST /admin/event-preparation | Администратор + разрешённый Origin | `{through}` с датой из подтверждения. При смене границы сервер требует новый предпросмотр (409). Повторный запрос во время очистки возвращает текущую операцию |

Список мероприятий, галерея, миниатюры, сведения о готовом ролике и медиа плееров поддерживают приватный кеш с ETag. При повторном запросе сервер проверяет доступ и актуальность ресурса перед ответом 304. Это распространяется на просмотр из архива, экрана результатов, редактора слота и по гостевой ссылке, включая подготовку файла для «Поделиться». Из архива ролик открывается в отдельной вкладке общего плеера. Обновление каждой вкладки сохраняет выбранное мероприятие или ролик.

Ключ первого мероприятия совпадает с датой, для следующих используется `YYYY-MM-DD~N`. Галерея, её медиа и удаление ограничены этим ключом. Закрытые сегодня мероприятия доступны в архиве с `closedToday: true`; удаление доступно со следующего дня.

`TodayDisplay` содержит ключ активного мероприятия `eventKey` (null между мероприятиями), `date`, `serverNow`, `pageDurationSeconds`, `sessions` и
`hiddenIds`. Последнее поле перечисляет ID вручную скрытых сегодня историй.
Клиент снимает их с активной страницы. Сервер исключает их из `sessions`.
Длительность хранится в singleton SQLite `display_settings`; существующий интервал
10 секунд используется до первого изменения администратором. Иные числа, строки,
неизвестные поля и изменение без разрешённого Origin отклоняются. Значение сохраняется
после перезапуска; оба аккаунта получают его в проекции экрана.

`DisplaySession.readyAt` — существующее `generation_jobs.ready_at` в миллисекундах
для готового видео, иначе null; отсутствующее историческое время не восстанавливается
догадкой. Порядок ответа остаётся по номеру/id, очередь готовности клиента использует
`readyAt` и стабильный порядок номера/id при отсутствии времени.

API карточки возвращает URL исходного фото, миниатюры первого снимка (`frameUrl` → `/cover`, JPEG до 640 px по длинной стороне), QR и защищённый
`videoUrl` для действия «Посмотреть». Композиция, меню и очереди —
[правила экрана](../states/results-display.md). Медиа проверяют права
соответствующего экрана; просмотр карточки не считается открытием формы посетителя.
Для эмуляции `DisplaySession` дополнительно содержит nullable `simulation`:
`{status: 'pending'|'passed'|'failed', message: string, detail: string|null}`. Поле заполняется только
для снимка с simulateGeneration=true; message/detail — согласованные подписи PRD
либо безопасная причина ошибки. Пока сессия capturing, она остаётся обычной съёмкой.
Для simulated card с видео/QR отсутствует; CloudClient показывает тестовый результат
в существующей карточке номера без шкалы завершённой реальной генерации.
При simulationOutput=video используются обычные stage/card и выдача; simulation
остаётся пометкой тестового происхождения, passed при ready. Архив добавляет
`testVideo: true` только этим сессиям; последнее реальное видео их исключает.
API не возвращает полные email, ключи и URLs fal. Отбор по времени и шесть этапов —
[жизненный цикл](../states/lifecycle-map.md#шесть-этапов-на-общем-экране).
Сегодняшний день не входит в архив и недоступен для удаления.

Проверки настройки, прав, сохранения и nullable readyAt:
`npx tsx --test tests/display-settings.test.ts tests/display.test.ts` — 4/4 PASS
при реализации 17 ноября 2026; внешние сервисы не вызываются.

## Получение и email

Страница QR — /receive/:token. Токен даёт доступ только к своей сессии.

| Операция | Результат |
|---|---|
| GET /receive/:token | Фото, номер, `videoUrl`/`downloadUrl`, состояние письма и доступность отправки |
| POST /receive/:token/opened | Фиксация открытия формы |
| POST /receive/:token/email | email → постановка письма на отправку |
| GET /download/:token (вне /api) | Собственное ready-видео, attachment; Range поддерживается |
| GET /download/:token?inline=1 (вне /api) | То же видео для встроенного плеера, inline; Range поддерживается |

Валидная QR-форма возвращает `videoUrl` и `downloadUrl` с уже существующим download-токеном
этой сессии. Смотреть и скачивать можно до ввода email. Чтение этих URL не меняет
`opened_at`, `email_confirmed_at` или состояние письма; открытие формы по-прежнему
фиксируется отдельным POST `/receive/:token/opened`. Receive- и download-токены
не взаимозаменяемы; ссылки не предоставляют доступ к другим сессиям или аккаунтам.

Сервер проверяет email и состояние: во время отправки второе письмо не запускается,
после успеха повтор запрещён, после ошибки возможен ручной повтор с исправлением адреса.
Потерянное подтверждение почтового сервиса не вызывает автоматическую повторную отправку.
Первое подтверждение email запускает трёхминутный срок, повтор его не меняет.
Состояние письма читается из той же формы; отдельного API истории попыток нет.
Удаление мероприятия закрывает выдачу по ссылкам. Медиа не доступны открытым каталогом.

## Граница генерации и выдачи

FT-003 подбирает URL шаблонов и снимков по [контракту файлов](integrations.md#файлы-и-срок-хранения),
подготовленное видео/кадр и затем собственную download-ссылку и receive-форму.
До готовности формы/ссылки сессия остаётся `preparing`; `ready` не означает отправку письма.
Для новых результатов до ready записывается `media/sessions/<id>/qr.png`, кодирующий
тот же receive-токен, который публикуется вместе с ready. QR старых ready-записей
без файла формируется по запросу. Перезапуск preparing повторяет подготовку QR;
удаление каталога сессии удаляет его вместе с остальными файлами. Миграция БД не нужна.
TASK-008 реализует страницу формы, GET её данных и POST opened/email с сохранением
`pending` и времени первого подтверждения по существующим правилам выше. Это позволяет
проверить доступную рабочую форму без зависимости генерации от SMTP.
FT-004 переиспользует эти маршруты/данные: добавляет SMTP-обработчик, QR/общий экран,
публичные этапы и скрытие. Пока почтовый обработчик не подключён, форма показывает
ожидание отправки, а не `sent`; фактическая доставка принимается в FT-004.
Данные готовой карточки (фото, кадр, номер, URL формы) готовит FT-003, публикует FT-004.
GET capture-state возвращает безопасный код/текст ошибки своей сессии; общий экран
ошибок реализуется в FT-004. Ответы клиентам не включают provider URLs и секреты.

## Диагностика видео

Открытая видимая страница запрашивает `GET /api/statuses/fal-balance` раз в минуту. Маршрут доступен оператору и администратору. Сервер использует `FAL_BILLING_KEY` или, если он пуст, `FAL_KEY`, объединяет запросы вкладок и при ошибке возвращает последнюю подтверждённую сумму со временем проверки.

Оператор и администратор читают `GET /api/statuses`. Без параметров возвращается текущий день по Новосибирску даже до первой сессии. Поле `eventName` содержит название мероприятия или `null`. Просмотр не создаёт запись мероприятия. Параметры `date`, `number`, `issues=1` и `before` ограничивают выборку. Ответ включает до 30 сессий, курсор по номеру, время сервера и число активных проблем за весь выбранный день. `GET /api/statuses/:id?after=<id события>` возвращает текущие факты из БД и до 100 событий в порядке записи с курсором продолжения. Для реального запроса fal поле `session.costUsd` (в списке — `sessions[].costUsd`) содержит `cost_total` в USD или `null` в ожидании. При чтении сервер отдельно запрашивает недостающие суммы по сохранённым `request_id` и сохраняет совпадения в SQLite. Чтение не открывает QR и не запускает генерацию. Для удаляемого или отсутствующего ID возвращается 404.

Параметр `requests=1` выбирает сессии с реальной попыткой отправки, а в истории сессии — события `fal.submit`. Записанное тело находится в `detail.providerRequest`. При отсутствии записи старой отправки поле `reconstructed` содержит доступную реконструкцию. Ссылки `/api/statuses/:id/photos/:number` (нумерация с 1) и `/api/statuses/:id/materials/:mediaId` выдают файлы этой сессии после входа оператора или администратора.

`POST /api/receive/:token/activity` принимает из формы получения UUID операции и одно из разрешённых действий скачивания или Web Share. Токен ограничивает сессию, проверяется Origin, повтор одного действия с тем же ID идемпотентен. Подтверждение 204 не свидетельствует о получении файла адресатом.
