# Внешние интеграции

Правила настройки и совместимости: [матрица](../../docs/slot-setup/matrix.md),
[план внедрения](../analysis/slot-setup-plan.md). Состояние реализации и проверки —
в [задачах](../tasks/index.json); правила legacy ниже относятся только к старым записям.

Основной сценарий задан [PRD](../prd.md), локальные состояния — [жизненным циклом](../states/lifecycle-map.md).
Это решения для реализации; реальные обращения к оборудованию и отправка писем ещё не проверены.

## Входы фотобудки

Локальный `/reelme.html` использует digiCamControl. Серверный `/booth` запускает тот же каталог и фотосессию с WebUSB и заголовками COOP/COEP. Ключ установки вводится для каждого origin отдельно. Вкладка открывает одну PTP-камеру Canon (USB VID 04A9) без ограничения по модели. «Canon OK» требует успешного открытия сессии, проверки возможностей и кадра Live View. Освобождение USB выполняется явно с ожиданием уже отправленного затвора. Пока камера подключена, раз в 15 с свободная очередь читает заряд через getConfig(). Ветка Canon EOS в libgphoto2 при этом запрашивает KeepDeviceOn, если камера поддерживает команду.

На `/booth` ручное нажатие сразу останавливает превью. В автоматической серии остановка начинается за 300 мс до конца настроенного отсчёта. После текущего чтения отправляются `viewfinder=false`, затем через 100 мс `captureImageAsFile()`. Обработчик ошибки настройки прикрепляется сразу. Полученный оригинал закрепляется за позой. При неопределённом результате следующий спуск требует явного действия. Аппаратная проверка серверной фотобудки на Canon ещё предстоит.

## Камера digiCamControl

CaptureClient работает в http://localhost:5513/reelme.html. При настройке включаются
веб-сервер, AllowWebserverActions, сохранение JPEG и неповторяющиеся имена снимков.
Одной камерой управляет только digiCamControl; DSLR Remote Pro на это время остановлен.

Для каждой позы адаптер читает /filelist.json, посылает GET /?CMD=Capture, затем ждёт
новый JPEG в списке и скачивает его по полю Original. Следующая съёмка начинается после
получения текущего кадра. HTTP-ответ затвора не означает готовность файла.
Список — массив FileName, Name, Width, Height, Original, SmallThumb, LargeThumb;
Original имеет вид /image/<имя>. Новизна определяется разницей списков.
[Обработчик digiCamControl](https://github.com/dukus/digiCamControl/blob/c420d401483799c16c60bda8ced1269a28a76e90/CameraControl.Core/Classes/WebServerModule.cs#L143-L198),
[поля ответа](https://github.com/dukus/digiCamControl/blob/c420d401483799c16c60bda8ced1269a28a76e90/CameraControl.Core/Classes/FileListItem.cs).

Live View запускается через /liveview.html?CMD=LiveViewWnd_Show, превью читается из
/liveview.jpg без кэширования. При активном Live View команда кадра —
/?CMD=LiveView_Capture. Зеркалится только экранное превью. Если оно нестабильно,
используются образец позы и отсчёт без превью; JPEG остаётся обязательным результатом.
[Штатный клиент](https://github.com/dukus/digiCamControl/blob/c420d401483799c16c60bda8ced1269a28a76e90/CameraControl.Application/WebServer/index.html#L48-L68).

При ошибке открытия, чтения или отображения превью установка через 1000 мс заново открывает Live View и запрашивает кадр. Неудача запускает следующую попытку с той же задержкой. Скрытие страницы и съёмка приостанавливают восстановление; кнопка «Продолжить без превью» отключает его до конца этой фотосессии.

Результат адаптера — JPEG Blob текущей позы либо понятная ошибка. Уже снятые Blob
остаются в текущей сессии: сбой облачной загрузки повторяет передачу, а не затвор.
Реализация — `src/client/capture/camera.ts`; интерфейс — `Capture.svelte`.
После отправленного затвора повтор продолжает ожидание того же файла (до 30 с
за попытку), сохраняя исходный список и выбранный Original. Второй затвор
автоматически не посылается: ответ мог потеряться после съёмки. Если JPEG
не появляется, требуется помощь сотрудника; текущий шаг остаётся незавершённым.
Признак pending остаётся действующим и после ошибки ожидания/скачивания JPEG;
до разрешения этой операции нельзя начать другой затвор, restart или retake.
Снятые Blobs с sessionId/poseIndex передаются владельцу через oncomplete только
при нажатии «Завершить фотосессию» или по истечении времени просмотра серии. До этого кадры и пересъёмки локальны.
Повтор передачи использует те же Blobs; восстановление их после reload не
предусмотрено. Маркер начала передачи запрещает возврат к скрытой пересъёмке
при потере локальных файлов; серверные принятые позиции сохраняются.

Настройка `sendCaptureLogs` закреплена за сессией. Включённая диагностика записывает успешные и неудачные попытки и связывает повтор с исходным кадром. Штатный журнал digiCamControl передаёт сотрудник. [Сбор и поиск случая](../../docs/MANUAL.md#диагностика-захвата-кадра).

Во время разработки целевая Canon недоступна: адаптер проверяется на управляемых
ответах этого HTTP-контракта и Linux-стенде ниже. На Canon EOS 1100D аппаратные проверки выполняются
в TASK-005 после завершения разработки приложения; тестовый стенд не заменяет испытание.

### Linux-альтернатива для разработки и тестов

На Linux вместо Windows digiCamControl можно использовать локальный сервер
[`linux_digiCamControl`](../../linux_digiCamControl/README.md). Он реализует необходимую
цепочку `Capture → filelist.json → Original/JPEG`; веб-камеры подключаются через
V4L2/FFmpeg, поддерживаемые фотоаппараты — через gPhoto2. Это замена части HTTP API,
не полная реализация digiCamControl. Основная камера текущего Linux-стенда по решению
оператора — HD User Facing (`/dev/video0`), режим 1280×720 MJPEG.

Запуск из корня репозитория:

```bash
python3 linux_digiCamControl/linux_digicamcontrol.py serve --camera /dev/video0 --size 1280x720 --input-format mjpeg
```

Тестовая страница — `http://localhost:5513/reelme-test.html`. Для CaptureClient
нужно передать `--web-root` с каталогом настроенного `reelme.html` по инструкции
[локальной страницы съёмки](../../docs/MANUAL.md#локальная-страница-съёмки), сохранив origin
`http://localhost:5513`. Для V4L2 поддержаны `LiveViewWnd_Show`, `/liveview.jpg`
и `LiveView_Capture`: один FFmpeg получает кадры, съёмка сохраняет следующий кадр,
не старое превью. `LiveViewWnd_Hide`/`Close` освобождает камеру; без запросов
preview/capture поток останавливается через 15 с. В тестовой странице
`/reelme-test.html` превью включается вместе с ручной серией: обновляется во время
отсчёта, уступает место оригинальному JPEG на 0,5 с, затем возвращается; после серии
выключается. При отказе preview серия может продолжиться без него, без повторного
спуска и удаления уже полученных фото. Отдельная диагностика — `/liveview.html`;
при сбое свежий JPEG не подменяется сохранённым снимком.
`/preview.jpg` — последний снимок, не Live View. gPhoto2 и mock не поддерживают
Live View (501); для них остаётся режим ReelMe без превью. `--camera mock` выдаёт
только синтетические JPEG.
Сервер слушает loopback; фотографии и журналы сохраняются локально в
`linux_digiCamControl/data/`. Проверки Linux-стенда не заменяют приёмку Windows/Canon
в TASK-005; результаты — [TESTING.md](../../linux_digiCamControl/TESTING.md).

## Почта

Администратор выбирает Mail.ru или SMTP.BZ в «Параметрах». Mail.ru использует адрес ящика как логин и отправителя, пароль приложения и TLS на `smtp.mail.ru:465`. Для SMTP.BZ задаются сервер, порт, логин, пароль и верифицированный отправитель. Профили хранятся в SQLite. До первого сохранения действуют прежние переменные окружения.
Тестовое письмо использует введённые реквизиты без активации. Очередь фиксирует отправителя для одного письма, включая резервную ссылку. Пароли и ответы провайдера исключены из API-ответов и логов.
[Пароль приложения Mail.ru](https://help.mail.ru/mail/faq/password/external/), [настройка SMTP.BZ](https://docs.smtp.bz/).

Вход адаптера: email, путь готового видео и собственная ссылка скачивания.
Видео прикладывается из файла на VPS через path/stream, без предварительной загрузки
всего ролика в память. Результат адаптера — подтверждённая отправка либо ошибка.
Подтверждение означает принятие почтовым сервисом, не получение или прочтение адресатом.
[Вложения Nodemailer](https://nodemailer.com/message/attachments).

Если прикрепление или письмо с вложением отклонено из-за файла/размера, отправляется
письмо со ссылкой. Ошибка подключения или авторизации не считается отказом вложения.
Если ответ потерян, показывается ошибка и возможная состоявшаяся отправка;
повторяет посетитель. После подтверждённого успеха повтор запрещён, как принято в PRD.

При подключении проверяются реальное MP4-вложение, резервное письмо и наличие подписи
SMTP.BZ на выбранном тарифе. Публичная документация не подтвердила предел размера и
отсутствие брендинга; этих гарантий спецификация не даёт. Это приёмка интеграции,
а не повод проектировать дополнительную почтовую систему. По решению оператора
реальная отправка не обязательна для закрытия разработки TASK-009: используются
локальные проверки на тестовом транспорте, фактическая доставка остаётся непроверенной.

## Генерация fal

Sessions получает snapshot и упорядоченные фотографии сохранённого плана,
собирает input по [матрице](../../docs/slot-setup/matrix.md) и
[схемам endpoint](../analysis/fal-api.md#модели). Индивидуальные Kling-наборы дают
отдельные Elements, группа — ordinary images перед дополнительными references.
Плоские модели получают фото участников в порядке съёмки, затем references;
Recast — один кадр каждого из 1/2 людей и необязательный непустой prompt.
`resolution`/`aspect_ratio` передаются только при поддержке endpoint, без crop/upscale.
Legacy snapshot без плана сохраняет прежние 1/4 фото и прежнюю валидацию параметров.
Используется серверный клиент fal: submit → сохранение request_id → polling status/result.
Webhook для первой версии не нужен. Встроенные retries fal остаются включёнными;
ошибка модели не запускает новую генерацию. При временном сбое скачивания сервер повторяет
запрос к сохранённому URL. HTTP 410 при скачивании означает окончательную потерю результата.

При успехе сохраняются URL результата и затем собственный видеофайл на VPS.
После скачивания ffprobe читает параметры видеодорожки, а FFmpeg извлекает один
JPEG для маршрута кадра ролика. При восстановлении подготовленной сессии публикация использует
сохранённые MP4 и JPEG. Обычная выдача и восстановление обходятся без полного
декодирования ролика. Модель выбирается явно; подмена альтернативной моделью отключается
через x-app-fal-disable-fallback. [Заголовки fal](https://fal.ai/docs/documentation/model-apis/common-parameters).

Для кадра ролика случайно выбирается целая секунда от 5 до 12 включительно.
Если выбранная точка достигает конца ролика или выходит за него, берётся длительность
минус случайные 1–3 секунды; отрицательная точка ограничивается нулём для коротких
роликов. JPEG извлекается до публикации ready, исходное видео не изменяется.
Карточка общего экрана использует миниатюру первого снимка сессии. Фото вписывается в область карточки через центрированный `object-fit: cover`:
лишнее сверху и снизу скрывается только при показе, сохранённый JPEG не обрезается.

### Проверка входов и тестовое видео без fal

Режим берётся только из сохранённой `generation`. При `simulateGeneration=true`
фотографии, материалы и запрос модели проходят обычную подготовку. Без
`simulationOutput` успех заканчивается `simulated`, ошибка — `failed`; выдачи нет.
С `simulationOutput=video` используется локальный transport: постоянный request ID
сессии, ожидание по сохранённому submitted_at, MP4 из `clientDir/test-videos` нужной
ориентации. Сетевого fallback нет, включая рестарт и ошибку чтения файла.

Далее действуют обычные prepareVideo/publishReady, QR, download и SMTP. Ready
невозможен без проверки видео/кадра/фото/QR; отправка email не эмулируется. Тестовые
result URLs внутренние и не передаются fal для удаления. Режим работает без FAL_KEY;
реальный запрос без ключа по-прежнему получает failed/FAL_NOT_CONFIGURED.

## Файлы и срок хранения

Фотографии посетителя выдаются fal с VPS по ссылкам `/provider-media/:token`, по одной на снимок.
После сохранения реального сценария сервер загружает в fal CDN его `videoId` и `referenceIds`.
SQLite хранит URL и срок по неизменяемому mediaId. Сессия выбирает ID из своего snapshot.
Для шаблона запрашивается 365 дней хранения. В последний час срока или при подтверждённом
HTTP 404/410 после ошибки генерации следующая отправка восстанавливает копию из локального оригинала.
Загрузка идёт в фоне, максимум по два файла одновременно. Симуляция использует локальные материалы.
При очистке мероприятия CDN-копия шаблона удаляется вместе с освобождённым локальным материалом.
[Хранилище fal](https://fal.ai/docs/documentation/model-apis/fal-cdn).

Основная копия результата находится на VPS. Для временного результата CDN fal задаётся
expiration_duration_seconds:86400 через X-Fal-Object-Lifecycle-Preference; файл скачивается
сразу после завершения генерации. X-Fal-Store-IO:0 отключает хранение JSON в истории fal.
Сутки — рабочий параметр временного хранения, не срок выдачи посетителю.
[Хранение fal](https://fal.ai/docs/documentation/model-apis/media-expiration).

У нас мероприятие удаляется вручную либо когда его календарная дата старше 14 дней
по Новосибирску. Удаляются принадлежащие ему файлы и закрываются их URL; используемые
материалы слотов сохраняются. Для известного выходного URL fal при очистке вызывается
его delete API; сбой записывается в лог, CDN-копия также имеет заданный срок истечения.
Удаление внутренних данных модели этим не гарантируется. Отдельная система сверки
всех копий провайдера не строится.
[Удаление файла fal](https://fal.ai/docs/documentation/model-apis/fal-cdn#deleting-files).
