# Внешние интеграции

Основной сценарий задан [PRD](../prd.md), локальные состояния — [жизненным циклом](../states/lifecycle-map.md).
Это решения для реализации; реальные обращения к оборудованию и отправка писем ещё не проверены.

## Камера digiCamControl

CaptureClient работает в http://localhost:5513/reelme.html. При настройке включаются
веб-сервер, AllowWebserverActions, сохранение JPEG и неповторяющиеся имена снимков.
Одной камерой управляет только digiCamControl; DSLR Remote Pro на это время остановлен.

Для каждой позы адаптер читает /filelist.json, посылает GET /?CMD=Capture, затем ждёт
новый JPEG в списке и скачивает его по полю Original. Следующая съёмка начинается после
получения текущего кадра. HTTP-ответ затвора не означает готовность файла.
Список — массив FileName, Name, Width, Height, Original, SmallThumb, LargeThumb;
Original имеет вид /image/<имя>. Новизна определяется разницей списков.
[Обработчик digiCamControl](https://github.com/dukus/digiCamControl/blob/c420d401483799c16c60bda8ced1269a28a76e90/CameraControl.Core/Classes/WebServerModule.cs#L143-L198),
[поля ответа](https://github.com/dukus/digiCamControl/blob/c420d401483799c16c60bda8ced1269a28a76e90/CameraControl.Core/Classes/FileListItem.cs).

Live View запускается через /liveview.html?CMD=LiveViewWnd_Show, превью читается из
/liveview.jpg без кэширования. При активном Live View команда кадра —
/?CMD=LiveView_Capture. Зеркалится только экранное превью. Если оно нестабильно,
используются образец позы и отсчёт без превью; JPEG остаётся обязательным результатом.
[Штатный клиент](https://github.com/dukus/digiCamControl/blob/c420d401483799c16c60bda8ced1269a28a76e90/CameraControl.Application/WebServer/index.html#L48-L68).

Результат адаптера — JPEG Blob текущей позы либо понятная ошибка. Уже снятые Blob
остаются в текущей сессии: сбой облачной загрузки повторяет передачу, а не затвор.
На Canon EOS 1100D это проверяется в задаче реализации; исходники не заменяют испытание.

## Почта SMTP.BZ

Sessions отправляет письма по SMTP через Nodemailer. Настройки подключения и адрес
отправителя задаются на сервере из кабинета SMTP.BZ; домен отправителя предварительно
верифицируется. Используется TLS, отдельная отправка через REST API не нужна.
[Настройка SMTP.BZ](https://docs.smtp.bz/), [транспорт Nodemailer](https://nodemailer.com/smtp).

Вход адаптера: email, путь готового видео и собственная ссылка скачивания.
Видео прикладывается из файла на VPS через path/stream, без предварительной загрузки
всего ролика в память. Результат адаптера — подтверждённая отправка либо ошибка.
Подтверждение означает принятие SMTP.BZ, не получение или прочтение адресатом.
[Вложения Nodemailer](https://nodemailer.com/message/attachments).

Если прикрепление или письмо с вложением отклонено из-за файла/размера, отправляется
письмо со ссылкой. Ошибка подключения или авторизации не считается отказом вложения.
Если ответ потерян, показывается ошибка и возможная состоявшаяся отправка;
повторяет посетитель. После подтверждённого успеха повтор запрещён, как принято в PRD.

При подключении проверяются реальное MP4-вложение, резервное письмо и наличие подписи
SMTP.BZ на выбранном тарифе. Публичная документация не подтвердила предел размера и
отсутствие брендинга; этих гарантий спецификация не даёт. Это приёмка интеграции,
а не повод проектировать дополнительную почтовую систему.

## Генерация fal

Sessions получает снимок сюжета и 1/4 фото, собирает input конкретной модели по
[проверенным схемам](../analysis/fal-api.md#модели) и отправляет его в очередь fal.
Используется серверный клиент fal: submit → сохранение request_id → polling status/result.
Webhook для первой версии не нужен. Встроенные retries fal остаются включёнными;
ошибка модели не запускает новую генерацию. Ошибка скачивания повторяет получение файла.

При успехе сохраняются URL результата и затем собственный видеофайл на VPS.
Техническая проверка воспроизводимости и получение кадра карточки выполняются через
FFmpeg/ffprobe; художественное качество не оценивается. Только после этого результат
становится ready. Модель выбирается явно; подмена альтернативной моделью отключается
через x-app-fal-disable-fallback. [Заголовки fal](https://fal.ai/docs/documentation/model-apis/common-parameters).
Разбор файла — [ffprobe](https://ffmpeg.org/ffprobe.html); извлечение кадра — FFmpeg.

## Файлы и срок хранения

Входные фото и материалы слотов остаются на VPS. fal получает прямые HTTPS-ссылки
вида /provider-media/:token без cookies/Authorization; токен открывает только один
файл, не список и не административный API. Для неизменного материала используется
тот же URL. Дополнительная загрузка входов в CDN fal не нужна.
[Внешнее хранилище fal](https://fal.ai/docs/documentation/model-apis/fal-cdn#using-your-own-storage).

Основная копия результата находится на VPS. Для временного результата CDN fal задаётся
expiration_duration_seconds:86400 через X-Fal-Object-Lifecycle-Preference; файл скачивается
сразу после завершения генерации. X-Fal-Store-IO:0 отключает хранение JSON в истории fal.
Сутки — рабочий параметр временного хранения, не срок выдачи посетителю.
[Хранение fal](https://fal.ai/docs/documentation/model-apis/media-expiration).

У нас мероприятие удаляется вручную либо когда его календарная дата старше 14 дней
по Новосибирску. Удаляются принадлежащие ему файлы и закрываются их URL; используемые
материалы слотов сохраняются. Для известного выходного URL fal при очистке вызывается
его delete API; сбой записывается в лог, CDN-копия также имеет заданный срок истечения.
Удаление внутренних данных модели этим не гарантируется. Отдельная система сверки
всех копий провайдера не строится.
[Удаление файла fal](https://fal.ai/docs/documentation/model-apis/fal-cdn#deleting-files).
