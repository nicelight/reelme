# Жизненный цикл фотосессии

Поведение задаёт [PRD](../prd.md), данные — [модель](../domains/core-domain.md).
Один серверный процесс обслуживает API и фоновую обработку; состояние хранится в SQLite.

## Съёмка и генерация

| Состояние | Значение |
|---|---|
| capturing | Сессия создана, принимаются 1/4 фото по снимку сюжета |
| submit_pending | Полный набор принят, запрос готовится к отправке в fal |
| observing | Сохранён fal ID, ожидается результат этого запроса |
| preparing | Результат скачивается и проверяется, готовится карточка |
| ready | Видео, собственная ссылка, форма и карточка готовы |
| failed | Окончательная ошибка, видимая у сессии |

Неудавшийся шаг камеры/загрузки повторяется без потери остальных кадров.
Завершение приёма проверяет полный набор и запускает обработку один раз.
Повтор завершения возвращает прежнее состояние. После приёма фото установка показывает
номер и готова к следующему посетителю, не ожидая генерации.

## Повторы fal и восстановление

Полученный request_id сохраняется; после этого новый submit не выполняется.
Сбой опроса повторяет опрос, сбой скачивания — скачивание того же результата.
COMPLETED проверяется вместе с результатом/ошибкой. После перезапуска сервер продолжает
работу по сохранённому состоянию и ID. Терминальная ошибка модели завершает обработку.
При потерянном подтверждении допустим дубль согласно принятому KISS-компромиссу;
отдельного механизма exactly-once нет. Невоспроизводимый файл не считается готовым.

## Отправка письма

Генерация остаётся ready. Отправка имеет собственное состояние:
not_requested → pending → sending → sent/failed.
При принятии email сохраняется время первого подтверждения формы; отсутствие отдельной
записи открытия восполняется, поскольку отправка формы уже означает её открытие.

Сначала отправляется вложение; если вложить файл не удалось — письмо со ссылкой.
Подтверждение SMTP.BZ означает sent, а не прочтение. При потере подтверждения показывается
ошибка с сообщением, что письмо могло уйти; посетитель повторяет вручную.
После перезапуска начатая, но не подтверждённая отправка также требует ручного повтора.
Во время отправки повтор не запускает новое письмо; после sent новая отправка запрещена.
После failed посетитель может исправить адрес и повторить. Отдельные ключи и история
всех почтовых попыток не нужны: решение принимает сервер по текущему состоянию сессии.

## Шесть этапов на общем экране

| Этап PRD | Условие |
|---|---|
| 1 — отправка | submit_pending |
| 2 — генерация | observing, включая очередь fal |
| 3 — подготовка | preparing |
| 4 — готово | ready, форма ещё не открывалась |
| 5 — получение | Форма открыта, успешного письма ещё нет |
| 6 — отправлено | SMTP.BZ подтвердил отправку; адрес замаскирован |

Съёмка не выдаётся за генерацию. Ошибка показывается отдельно, без ложного успеха.
Карточка и строка скрываются через три минуты от первого подтверждения email,
независимо от успеха письма. Форма и архив остаются доступны до удаления мероприятия.
Срок определяется сохранённым временем и не сбрасывается при рестарте/повторе.

## Удаление

Администратор удаляет только прошедшие дни. Автоочистка удаляет мероприятия старше
14 календарных дней по Новосибирску. Общие материалы слотов сохраняются, пока используются.
Удаляемое мероприятие скрывается, новые операции для него прекращаются. Обработчик
проверяет этот признак перед публикацией результата. Незавершённая очистка продолжается
после рестарта; отдельный журнал гонок удаления и аварий файловой системы не вводится.
Входы fal выдаются с VPS, результат сохраняется у нас; срок CDN-копии и её удаление
заданы в [контракте файлов](../contracts/integrations.md#файлы-и-срок-хранения).

## Проверки при реализации

- Практическая работа камеры, fal и SMTP.BZ по [контрактам](../contracts/integrations.md).
- Воспроизводимость результата, вложение/резервная ссылка и удаление файлов мероприятия.
Обычные таймауты, интервалы опроса и расположение файлов выбираются при реализации;
они не требуют отдельного этапа согласований или схем защиты от редких сочетаний сбоев.
