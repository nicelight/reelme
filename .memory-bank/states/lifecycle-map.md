# Жизненный цикл фотосессии

Правила настройки и совместимости: [матрица](../../docs/slot-setup/matrix.md),
[план внедрения](../analysis/slot-setup-plan.md). Состояние реализации и проверки —
в [задачах](../tasks/index.json); правила legacy ниже относятся только к старым записям.

Поведение задаёт [PRD](../prd.md), данные — [модель](../domains/core-domain.md).
Один серверный процесс обслуживает API и фоновую обработку; состояние хранится в SQLite.

## Локальная съёмка до передачи

До Finish JPEG находятся в памяти клиента, uploads отсутствуют. Отсчёт, ожидание
камеры и односекундное подтверждение кадра выполняются последовательно. Длительность отсчёта фиксируется при старте (по умолчанию 5 секунд).
В ручном режиме каждый тап по Live View запускает один отсчёт и кадр. Play
включает автоматическую серию. Pause возвращает ручной режим и отменяет
текущий отсчёт. Pause при уже отправленном
спуске сохраняет получение и подтверждение текущего JPEG, но останавливает дальнейшую автоматику. Перед вторым
человеком — ожидание готовности. Подтверждённый Restart очищает серию и возвращает первую позицию в текущем режиме. Retake сразу убирает последнюю позицию и миниатюру для пересъёмки,
сохраняя остальные. Pending JPEG блокирует пересъёмки и смену сюжета даже при
ошибке получения. Диалоги останавливают отсчёт; отмена сохраняет серию. Подтверждение
смены сюжета возвращает каталог, освобождая только локальные кадры.
После последнего кадра начинается review. Кнопка «Завершить фотосессию» или истечение
таймера передаёт принятые Blobs в upload/finalize. Образец берётся из snapshot и виден весь countdown.
Превью отменяется до спуска и не опрашивается до конца подтверждения JPEG;
в это время показываются белая live-область, затем снятый кадр. После подтверждения
возвращается live, включая review. Скрытие вкладки останавливает preview polling;
старый запрос не может заменить кадр после отмены или unmount.
Pause→Play во время подтверждения сохраняет его исходный секундный deadline:
следующий отсчёт ждёт остаток показа, не начинает секунду заново.

После Finish камера не вызывается повтором передачи. Reload с полным набором на
сервере позволяет дозавершение; при потере недостающих Blobs — явная остановка,
без пересъёмки или неполного finalize. Новый сеанс не удаляет принятые позиции
прежнего. Хранятся только receipt/маркер, без JPEG в Web Storage/IndexedDB.

## Съёмка и генерация

| Состояние | Значение |
|---|---|
| capturing | Сессия создана, принимаются позиции сохранённого плана (legacy: 1/4 фото) |
| submit_pending | Полный набор принят, запрос готовится к отправке в fal |
| observing | Сохранён fal ID, ожидается результат этого запроса |
| preparing | Результат скачивается и проверяется, готовится карточка |
| ready | Видео, собственная ссылка, форма и карточка готовы |
| simulated | Подготовка входов успешна; fal не вызывался, видео и выдачи нет |
| failed | Окончательная ошибка, видимая у сессии |

Неудавшийся шаг камеры/загрузки повторяется без потери остальных кадров.
Завершение приёма проверяет полный набор и запускает обработку один раз.
Повтор завершения возвращает прежнее состояние. После приёма фото установка показывает
номер и готова к следующему посетителю, не ожидая генерации.

## Эмуляция и ручной тест

После полного приёма/finalize сессия с simulateGeneration=true проходит обычную
подготовку фото/материалов/model input. Без simulationOutput успех завершает
submit_pending → simulated, ошибка даёт failed; ready/выдача не создаются.
При simulationOutput=video используются обычные submit_pending → observing →
preparing → ready и последующие состояния получения/email, но локальный transport
вместо fal. Режим и очередь восстанавливаются из snapshot/request_id/submitted_at;
настройка текущего слота не влияет. Ошибки не переключают сессию на реальный fal.
Старые снимки с true без output остаются input-only. False сохраняет реальный путь.

Ручной тест администратора использует тот же startRequestId, дату/номер, снимок,
приём отдельных JPEG по сохранённому плану и finalize (legacy: прежние 1/4 позиции). Пока файлы не приняты, сессия capturing и worker её не берёт.
Повтор принятого запроса возвращает ту же сессию, без второй подготовки/генерации;
конкурентная незавершённая подготовка даёт 409 TEST_IN_PROGRESS. Ошибка после создания
сессии сохраняется как failed/TEST_PREPARATION_FAILED; повтор того же ID возвращает
этот исход, новый ручной тест использует новый ID. После рестарта оставшаяся capturing
тестовая сессия может быть продолжена тем же запросом с ранее зафиксированными входами;
реализация не должна повторно submit уже финализированную сессию.

На общем экране simulated показывает согласованные подписи PRD без fake QR/ролика
и без заполненной шкалы успеха реальной генерации. Ошибка эмуляции содержит безопасную
причину подготовки. Поскольку email-подтверждения нет, такие карточки остаются в
сегодняшнем списке до смены даты; затем хранятся в обычном архиве/retention без видео.

## Повторы fal и восстановление

Полученный request_id сохраняется; после этого новый submit не выполняется.
После временного сбоя сервер повторяет опрос или скачивание того же результата.
HTTP 410 при скачивании переводит сессию из `preparing` в `failed`.
COMPLETED проверяется вместе с результатом/ошибкой. После перезапуска сервер продолжает
работу по сохранённому состоянию и ID. Терминальная ошибка модели завершает обработку.
При потерянном подтверждении допустим дубль согласно принятому KISS-компромиссу;
отдельного механизма exactly-once нет. Невоспроизводимый файл не считается готовым.

## Отправка письма

Генерация остаётся ready. Отправка имеет собственное состояние:
not_requested → pending → sending → sent/failed.
При принятии email сохраняется время первого подтверждения формы; отсутствие отдельной
записи открытия восполняется, поскольку отправка формы уже означает её открытие.

Сначала отправляется вложение; если вложить файл не удалось — письмо со ссылкой.
Подтверждение SMTP.BZ означает sent, а не прочтение. При потере подтверждения показывается
ошибка с сообщением, что письмо могло уйти; посетитель повторяет вручную.
После перезапуска начатая, но не подтверждённая отправка также требует ручного повтора.
Во время отправки повтор не запускает новое письмо; после sent новая отправка запрещена.
После failed посетитель может исправить адрес и повторить. Отдельные ключи и история
всех почтовых попыток не нужны: решение принимает сервер по текущему состоянию сессии.

## Шесть этапов на общем экране

| Этап PRD | Условие |
|---|---|
| 1 — отправка | submit_pending |
| 2 — генерация | observing, включая очередь fal |
| 3 — подготовка | preparing |
| 4 — готово | ready, форма ещё не открывалась |
| 5 — получение | Форма открыта, успешного письма ещё нет |
| 6 — отправлено | SMTP.BZ подтвердил отправку; адрес замаскирован |

Съёмка не выдаётся за генерацию. Ошибка показывается отдельно, без ложного успеха.
Карточка и строка скрываются через три минуты от первого подтверждения email,
независимо от успеха письма. Форма и архив остаются доступны до удаления мероприятия.
Срок определяется сохранённым временем и не сбрасывается при рестарте/повторе.

## Удаление

Администратор удаляет только прошедшие дни. Автоочистка удаляет мероприятия старше
14 календарных дней по Новосибирску. Общие материалы слотов сохраняются, пока используются.
Удаляемое мероприятие скрывается, новые операции для него прекращаются. Обработчик
проверяет этот признак перед публикацией результата. Незавершённая очистка продолжается
после рестарта; отдельный журнал гонок удаления и аварий файловой системы не вводится.
Порядок хранения и удаления входных материалов и результатов задан в [контракте файлов](../contracts/integrations.md#файлы-и-срок-хранения).

## Проверки при реализации

- Практическая работа камеры, fal и SMTP.BZ по [контрактам](../contracts/integrations.md).
- Воспроизводимость результата, вложение/резервная ссылка и удаление файлов мероприятия.
Обычные таймауты, интервалы опроса и расположение файлов выбираются при реализации;
они не требуют отдельного этапа согласований или схем защиты от редких сочетаний сбоев.

## Диагностика сессии

Правила [страницы статусов](../features/FT-007-session-statuses.md). Состояния сессии, задания и выдачи остаются источником текущего результата. Журнал дополняет их сведениями о подшагах и переходах, которые сегодня перезаписываются. Строка показывает детальный шаг только пока он согласуется с текущим состоянием. Готовность видео сохраняется при любом исходе выдачи.

| Участок | Наблюдаемые события |
|---|---|
| Приём | Создание сессии и номера, первый и заменённый JPEG по позиции, количество из плана, отказ при приёме известной сессии, успешный finalize. Повтор старта с тем же ключом и повтор finalize не создают вторую сессию или переход. Основная история доступна и при выключенных подробных capture-reports. |
| Входы модели | Слот и модель из snapshot, режим (боевой, ручной тест, эмуляция, тестовое видео), проверка локальных входов. Ожидание, готовность, ошибка или восстановление общих шаблонов CDN только в части, затрагивающей эту сессию. Процент байтов и счётчик файлов в админке относятся к общей загрузке материалов слота. |
| fal | Начало вызова submit, подтверждение и сохранённый request_id, известный HTTP-отказ либо ответ не получен. При потере ответа принятие и стоимость неизвестны, штатный повтор может создать второе задание. Считать видимые вызовы приложения; внутренние retries SDK могут быть непрозрачны. Различать смену статуса очереди, временную ошибку опроса, терминальную ошибку модели и получение результата. Для ошибки в истории сотрудника и её JSON сохранять короткое безопасное пояснение fal и известное имя поля, если они доступны. После сохранения ID используется тот же job. |
| Локальная подготовка | Получение адреса результата без записи URL в журнал, скачивание MP4, проверка контейнера, извлечение кадра, подготовка QR и публикация ready. Для ошибки указывать операцию, безопасный код, HTTP-статус при наличии и разрешённый текущей логикой повтор. Долгое молчание показывать как давность последнего наблюдения. |
| Выдача | Открытие формы; намерение скачать и отдельно серверный исход передачи (завершена на стороне сервера, прервана или неизвестна). Различать inline-плеер, фоновую подготовку файла для Share и обычную выдачу attachment, в том числе по ссылке из письма. HEAD, Range/206 и предварительная загрузка не означают завершённое скачивание. Успешный HTTP-ответ не доказывает запись файла на устройство. |
| Share и почта | Вызов Web Share и наблюдённый исход promise (завершён, отменён, ошибка); получение адресатом неизвестно. Сохранение запроса email, попытка SMTP, переход от вложения к ссылке, принятие SMTP, отказ или неизвестный исход после обрыва. Указывать способ отправки. Клиентский сигнал не устанавливает серверный статус выдачи. |

**Формат.** Ограниченная SQLite-история с FK на sessionId и каскадным удалением. У записи есть монотонный идентификатор для порядка при одинаковом времени, серверное время UTC, источник, этап, код события и исход. В разрешённых полях — номер прикладной попытки и её операция, модель, fal request_id после подтверждения, индекс фото, HTTP-статус, нормализованный код ошибки и число одинаковых повторов, где применимо. Контекст выгрузки включает версию формата, sessionId, дату мероприятия, номер посетителя и текущий серверный статус. Человек видит время с часовым поясом и короткие русские подписи. Пример записи:

```json
{"id":42,"at":"2026-11-21T12:04:33Z","sessionId":"example-session","source":"worker","step":"fal.submit","event":"ack_missing","outcome":"unknown","attempt":1}
```

**Доступ и объём.** Два запроса только для чтения — список по дате с постраничным чтением и история по sessionId с курсором. Запрашивать детали при раскрытии, историю целиком при копировании, без выдачи чужих сессий или обрезки без отметки. Поля строго перечислены: исключить адреса email, IP, сырой User-Agent, URL, токены, промпты, тела ответов и stack traces. Клиентские сообщения о выдаче принимаются только для сессии валидной receive-ссылки с проверкой origin, кодов, размера, повторов и частоты. Они остаются помеченными как сообщения браузера. Плеер и Share различать по назначению запроса, сохраняя общий путь проверки download-токена и совместимость старых ссылок.

**Надёжность.** Регистрировать результаты бизнес-переходов после их фиксации. Сбой диагностической вставки не должен попасть в обработчик ошибки submit, откатить приём фото, сорвать HTTP-поток или превратить ready в failed. Сбой отметки о начале попытки тоже не прерывает рабочий вызов. Браузерная телеметрия не задерживает переход по ссылке или синхронный вызов Web Share из жеста пользователя. Без новой очереди, внешнего сборщика, повторных запросов в fal и SMTP для диагностики. Схлопывать одинаковые poll/retry (первое и последнее время, число повторов), ограничить число записей выдачи на сессию с явной отметкой о сокращении. Ошибку записи сигнализировать ограниченным по частоте сообщением в серверный лог. После аварии возможен пробел между бизнес-операцией и записью. Для старых и неполных историй показывать доступные факты из БД с их источником, без вымышленных событий и времени.

**Необязательная детализация получателя.** Если включена, использовать случайную метку браузерного профиля в пределах одной сессии выдачи. Отображать «два профиля открыли/запросили файл» только с привязкой к соответствующим действиям. Один телефон с двумя браузерами может дать две метки. Прямая ссылка, приватный режим или запрет хранения допускают неизвестный профиль. Исключить fingerprinting и связывание посетителей между мероприятиями. Отсутствие метки допускается при приёмке.
