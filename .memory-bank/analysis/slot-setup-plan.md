# План внедрения настроек слотов

Цель — **работающий переработанный интерфейс слотов и фотосессии**, включая
согласованную серверную обработку. Матрица и готовые промпты — подготовительная
часть, не конечный результат. Индексированные задачи нового объёма приведены
ниже; реализация и проверки записываются в их карточках.

По прямому указанию оператора **не тестировать все 800+ вариантов промптов**.
В задачах предусмотреть только представительные примеры и существенные границы;
не добавлять полный перебор в unit/API/UI, CI или реальные генерации.

Основание: [матрица состояний и моделей](../../docs/slot-setup/matrix.md).
Шаблоны и API-отчёты связаны из каждой строки матрицы, тексты промптов здесь не повторяются.
План касается FT-001/002/003/006. Подготовлены машинная матрица, готовые промпты
и lookup-функция; они ещё не подключены к редактору и модельному pipeline.
Лимиты согласованы: использовать документацию API без дополнительных ограничений
для перестраховки. Источники, неоднозначности и выбранные трактовки сохранены
в матрице; возможные расхождения реальных запросов разбираются при отладке.

## Согласованные интерфейсы внедрения

- `SlotInput`: `participants: 1 | 2 | 'group'`, `photosPerParticipant: number`,
  `orientation: 'landscape' | 'portrait'`, `aspectRatio?: string`; строгая проверка
  нового сохранения по общей матрице. Разные предварительные количества кадров
  двух людей — состояние редактора, а сохранённый setup всегда равный.
- `SlotSnapshot.posePlan?: Pose[]`, `expectedPhotos: number`; в новом snapshot
  число равно длине конкретного плана. `Pose` сохраняет `index/key/instruction`,
  добавляет `participant: 1 | 2 | 'group'`, `guideNumber: 1..5`,
  `guideMediaId?: UUID`; новые поля допускают отсутствие у legacy-поз.
  API start/status возвращает сохранённый план.
- Отсутствие `posePlan` отличает старый snapshot: старые 1/4, позы и payload
  сохраняются, `generation` не перепроверяется новой матрицей. Несохранённый заново
  raw legacy-слот при запуске остаётся на этом пути; editor нормализует его для
  отображения, первое новое сохранение переводит его на новый setup. История
  не переписывается.
- `testPhotoIds?: UUID[]` — только активные JPEG в порядке `posePlan`, вне
  `generation`; `testPhotoId` остаётся для legacy retry. UI-кеш ключуется человеком
  и ракурсом либо группой, сервер не принимает лишний кеш как вход модели.
- Новый V2V draft можно сохранить без `videoId`; start/test отклоняют запуск,
  каталог явно не позволяет его начать. Фиксация редактора не является серверным lock.
- Создание слота принимает необязательный UUID `id` в POST envelope, вне
  persisted `SlotInput`; editor заранее создаёт его через `crypto.randomUUID()`.
  PUT сохраняет существующую идентичность.
- `POST /api/admin/slots/:id/template-video` с `{orientation, model}` возвращает
  проверенный `Media`; допускает UUID нового draft. Сервер выбирает строго
  `<UUID>__<orientation>.mp4`, импортирует в immutable media; nullable
  `slot_media.template_slot_id/template_orientation` фиксируют принадлежность.
  Сохранение проверяет эту принадлежность. Start не импортирует файл заново.
- `GET /api/admin/capture-guides` возвращает `{number,instruction,mediaId?}[]`;
  `PUT /api/admin/capture-guides/:number` принимает `{mediaId: UUID | null}`.
  Обе операции admin-only; инструкция задаётся согласованной позой.
  `GET /api/capture/sessions/:id/guides/:number` требует ключ установки и выдаёт
  только media, закреплённое в `posePlan` этой сессии.

## 1. Единый план съёмки и входов модели

**Результат:** редактор, сервер, тестовый запуск и fal-адаптер используют одинаковое
распределение фотографий; уже начатые сессии продолжают прежний план.

- Расширить текущие модели/валидацию в `src/shared/scenarios.ts`: персонажи,
  кадры, качество, ориентация/ratio и отдельные правила вместимости. Не заводить
  универсальный workflow engine или отдельный язык описания ограничений.
- Вынести только необходимый чистый расчёт setup в shared-модуль. Он возвращает
  доступные варианты, распределение по людям, ordinary/Element-входы, остаток,
  ошибку фиксации и упорядоченные позиции съёмки.
- `src/shared/capture.ts`: позиция содержит уникальный индекс, номер человека
  (либо группу), номер ракурса, инструкцию и ссылку на образец. В новом snapshot
  сохранить конкретный план, число кадров и настройки; не пересчитывать их
  позже из изменяемого каталога моделей или текущей страницы ракурсов.
- `scenarios/store.ts`, `sessions/index.ts`, `sessions/generation.ts`,
  `sessions/model-input.ts`: снять ограничения `1 | 4`, regex индексов `0..3`
  и конструирование одного Element для всех случаев. В `db.ts` мигрировать
  `capture_photos` с прежнего CHECK `pose_index BETWEEN 0 AND 3`, сохранив строки,
  `provider_media` FK/токены и действующие URL. Проверять полноту плана
  и роли каждого файла; новые диапазоны до восьми кадров не влияют на нумерацию сессий.
- Для Kling собирать C Elements либо групповые ordinary images; остальные P2V
  получают упорядоченные плоские списки. Recast — один файл на человека, пустой
  prompt не отправлять. Передавать resolution/aspect_ratio только при наличии
  соответствующего параметра endpoint, с его точным регистром и типом.
- Старые слоты при открытии получают прежние смысловые значения: один человек,
  Recast 1 кадр, остальные 4. Новые сохранения проверяются по новым правилам.
  Незаново сохранённые legacy-слоты запускаются по прежнему пути; нормализация
  при открытии редактора сама их не мигрирует. Старые snapshot без нового плана
  продолжают прежние позы и входы; не переписывать
  историю и результаты миграцией. Старые неподдерживаемые теперь UI-значения
  разрешений показывать явно и требовать выбрать допустимое при новой настройке.

**Проверки:** выборка разных способов передачи фото/Elements и числа участников;
ограничения выходных параметров;
примерные бюджеты 5/12/2; границы одного Element и общей группы; отдельные payload
всех 11 endpoint; старый snapshot; прямой невалидный запрос в обход UI. Проверки
используют локальные файлы и перехваченный fal transport, без платных вызовов.

## 2. Последовательный редактор, промпты и тестовые наборы

**Результат:** настроенный слот нельзя случайно запустить с фотографиями или
промптом от другого setup; ручные правки сохраняются в согласованных случаях.

- В `src/client/cloud/App.svelte` реализовать состояния и сбросы из матрицы.
  Не менять карточку слота при разблокировке генерационных настроек. Фиксация
  — состояние редактора, сервер сохраняет только проверенный setup; отдельный
  сетевой протокол «взять lock» не нужен.
- Выводить раздельно вместимость камеры, обычные референсы и Elements. Вместо
  текущих трёх полей references строить нужное число по остатку, включая V2V,
  где endpoint допускает дополнительные обычные изображения.
- Поддержать запрошенные разрешения/ориентации; недоступные опции объяснять.
  Для endpoints без aspect_ratio сверять исходник. P2V-длительность остаётся
  верхним параметром, ограниченным выбранной моделью.
- Использовать уже подготовленные `src/shared/slot-setup-matrix.json`,
  `selectSlotPrompt()` и 813 файлов `public/slot-prompts/**/*.md`.
  Выбранный файл загружается целиком и вставляется как обычный текст, без
  сборки, подстановок, Markdown-rendering, описания слота или LLM в runtime.
  Офлайн-генератор служит только разработке. Одинаковые копии разрешены оператором.
  Точные ключи и примеры — [каталог](../../docs/slot-setup/prompt-catalog.md).
- При подключении добавить выдачу `/slot-prompts/` из `dist/client/slot-prompts`
  с обычной ревалидацией кеша: существующая раздача `/assets/` их не охватывает,
  а годовой immutable-cache не подходит стабильным именам. Обработать ошибку
  загрузки и отменять/игнорировать устаревшие ответы при смене setup или ручной правке.
- Отслеживать шаблонный/ручной текст. References при шаблонном тексте обновляют
  его; при ручном — сохраняют и вызывают напоминание. Смена верхнего setup
  восстанавливает общий шаблон; Recast восстанавливает пустое поле.
- Вместо `testPhotoId` сохранять `testPhotoIds` в порядке плана; UI-кеш
  назначает отдельные изображения по персонажу/ракурсу или группе. Кешировать только IDs/Blob-ссылки нужных фото,
  не сериализовать JPEG/base64 в Web Storage. Группа и индивидуальные люди
  используют разные ключи; лишний кеш никогда не расширяет отправляемый набор.
  Использовать существующую загрузку/хранение медиа; отдельный кеш-сервис не нужен.
- `SlotTest.svelte`, `sessions/index.ts`, `scenarios/store.ts` и очистка материалов:
  проверять все нужные JPEG, фиксировать именно выбранный набор в тестовой сессии,
  копировать каждый на свою позицию. Идемпотентность ручного запуска сохраняется.
  Старый единственный fixture не размножать для нового многокадрового теста;
  незавершённый старый тест продолжает прежний snapshot.
- Панель «Тесты» управляет раскрытием; существующая фейковая генерация остаётся
  отдельной явной настройкой. Последний ready-результат и уже начатый тест
  не удалять при сбросе формы.

**Проверки:** последовательное раскрытие, неравный набор и текст ошибки, lock/unlock,
сброс нижних полей, ручной/шаблонный prompt, предупреждение после смены references,
переключение 1/2/3+ без смешивания тестовых фото, тест по полному/неполному набору,
безопасный повтор запуска и сохранность чужих сессий при очистке материалов.

## 3. Шаблонные видео и пять образцов ракурсов

**Результат:** плеер показывает связанный со слотом исходник; камера получает
админские образцы поз, которые не меняются посреди начатой фотосессии.

- Подготовительная часть выполнена: [media/template-videos/readme_media.md](../../media/template-videos/readme_media.md).
  Реальных роликов пока нет. Не добавлять случайные демонстрационные видео.
- При реализации привязки использовать slot ID и вариант ориентации из имён
  файлов. Для нового слота обеспечить стабильный ID черновика до подготовки файла;
  API создания должен сохранить этот ID либо вернуть его до привязки.
  Это часть существующей идентичности слота, не отдельный реестр шаблонов.
- Проверять исходник через существующий media-путь/ffprobe и копировать в
  immutable media storage. Слот/snapshot ссылается на media ID; ни перезапись
  исходного файла, ни смена ориентации слота не меняют старый snapshot.
- В редакторе заменить пользовательский upload V2V на плеер и статус фиксированной
  привязки. Без подходящего файла показывать причину неготовности; сохранение
  черновика и готовность к запуску не должны подставлять чужой ролик.
  P2V-демовидео остаётся только демонстрацией и не входит в fal payload.
- Добавить админскую страницу пяти именованных поз и admin-only чтение/обновление
  их конфигурации. Файлы проходят существующую проверку изображений; загруженная
  замена получает новый media ID. Клиент камеры получает образец из плана сессии,
  через защищённую выдачу, без admin-доступа и без попадания образца в fal.
- Учитывать текущие и закреплённые за сессиями образцы при очистке медиа. Если
  изображение ещё не загружено, показывать инструкцию и честный placeholder;
  не использовать старую SVG-позу с другим смыслом.

**Проверки:** права администратора; соответствие имён и реальных видео-параметров;
отсутствующий/несовместимый исходник; плеер с Range; смена media при начатой сессии;
пять поз и fallback; отсутствие этих образцов в модельном запросе.

## 4. Управляемая фотосессия

**Результат:** оператор может подготовить людей и переснять кадры до отправки;
в генерацию попадает только окончательно принятая последовательность.

- `Capture.svelte` использует готовый план с индивидом/группой и повторно применяет
  те же ракурсы для второго человека. Перед сменой человека — ожидание продолжения.
  `PoseGuide.svelte` показывает нужный образец весь countdown; группа всегда №5.
- Pause останавливает countdown; Continue начинает полные 3–2–1. Обработка ожидает
  один camera.capture; во время получения JPEG не допускаются второй спуск,
  сдвиг текущего индекса и удаление результата незавершённой операции.
- `Restart фотосессия` сбрасывает локальную серию до первого кадра;
  `Перефоткать последнее` заменяет последнюю завершённую позицию, сохраняя остальные.
  Оба действия останавливают автоматическое продвижение и ждут готовности.
- После последнего снимка показывать review с «Завершить фотосессию».
  `PhotoSession.svelte` получает финальные Blobs только после этой кнопки;
  дальше действуют существующие upload/retry/finalize. Граница пересъёмки —
  начало передачи по кнопке, а не получение ответа fal. При восстановлении
  частично отправленной серии сохраняются принятые позиции и путь дозавершения;
  они не стираются локальным Restart. По решению оператора KISS: без IndexedDB
  для JPEG. Повтор передачи использует RAM; при reload и потере недостающих Blobs
  показывать явную остановку, не снимать снова и не финализировать неполный набор.
  Маркер начала передачи может храниться без байтов фото в sessionStorage.
- Освобождать object URLs и отменять локальные таймеры при пересъёмке/уходе;
  это предотвращает поздний спуск или отображение старого кадра. Live View и
  существующий режим без превью сохраняются.

**Проверки:** pause на 3/2/1; continue; restart после нескольких кадров; пересъёмка
последнего кадра на границе двух людей и в конце серии; ни одного submit до
завершения; ошибка камеры и передачи; отсутствие повторного shutter после ухода;
два последовательных посетителя. Во время разработки — управляемая камера;
аппаратная приёмка Canon/digiCamControl остаётся отдельной реальной проверкой.

Задачи зависят друг от друга последовательно; проверки входят в каждый результат.
Владение частями общих AC явно указано в карточках. Обновлять контракты/требования
вместе с реализацией; историю завершённых задач и доказательств не переписывать.
Аппаратная приёмка остаётся в TASK-005 и не блокирует разработку.

В заголовке каждого нового или существенно изменённого модуля, использующего
эту матрицу, добавить `docs/slot-setup/matrix.md` как Source
в существующем Module contract; Svelte — внутри начального script. Не добавлять
ссылки в не затронутые файлы только ради покрытия.

Финальные проверки: `npm run check`, `npm run build`, затронутые unit/API-тесты,
затем проектный browser smoke редактора и камеры. Проверить на узком и широком
экране длинные объяснения бюджетов, недоступные варианты и одновременный показ
образца/отсчёта. Оплачиваемые fal-вызовы, продакшен и реальная камера не считаются
проверенными локальными моками; здесь они не запускались и не требуются для плана.

KISS-ограничения: фото не анализируются на число лиц/позу; нет распознавания монтажа,
кропа/апскейла, LLM-переписывания промптов, универсального workflow engine и
обязательного сохранения браузерного кеша после закрытия. Ручной prompt может
содержать устаревшие ссылки после правки references — это принятое поведение
с напоминанием, а не повод незаметно затирать авторский текст.

История подготовки (не требование повторять полный перебор): проверены 108 строк
съёмки и 813 готовых `.md`-промптов, в том числе
два пустых Recast. `check:slot-prompts`, четыре теста выбора/бюджетов/токенов,
`npm run check` и `npm run build` прошли; Vite скопировал все assets без изменения
байтов. Lookup ещё не подключён к редактору. Камера, UI новых настроек и реальные
fal-запросы этим не проверены. Продолжение — [handoff](../../agent_session_handoff.md).
